# 智能体运行中编辑正文设计

> 状态：设计定稿，一期实现中（2026-10-19）。本文是实现依据；后续改动如需偏离，先改本文再改代码。

## 1 背景与目标

群友反馈：让智能体校对第一章时，右侧编辑器整本只读，不能先去写第二、三章，哪怕智能体根本没读那几章。

目标：智能体运行期间和提案待审期间，正文编辑不再被禁止。用户与智能体同时改同一篇时可能冲突，这个风险交给用户：系统负责发现冲突并说明清楚，由用户决定保留哪一版，绝不静默覆盖任何一方。

一期目标：

- 短篇、剧本：运行中、提案待审时都能编辑，自动保存照常进行。
- 接受提案时按文档校验基线：智能体读取后被改过的文档不直接落盘，改为让用户选择“保留我的”或“用智能体版本覆盖”。
- 长篇：正文类写入在 Core 落盘前校验基线，消除现有的静默覆盖窗口。
- 自动审批遇到基线不符时暂停这一条，转为手动处理。

一期不做：三方合并与逐段选择、长篇接受提案时的整本短暂锁、结构操作（增删、移动、重命名小节或章节）放开，详见第 9 节。

## 2 现状与根因

### 2.1 锁在哪里

- 短篇、剧本：`useLongWorkspacePresentationCoordinator.editorLocked` 里调用 `documentHasWriteBarrier`，作用域是整本书（`book:<id>`）。该书任一会话正在运行（busy）或有待审提案，整本只读。`WorkspaceShell` 的自动保存 `isWriteBlocked` 和“全部排版”也被同一条件拦住。
- 长篇：运行中本身不锁，只在同步刷新、发送前保存、接受提案时短暂锁整本（`longEditorLocked`）。

### 2.2 锁其实承担着安全职责

接受提案时，两条路径都不校验“智能体读的版本是不是磁盘现在的版本”：

- 短篇：`saveDocument` 带 `force: true`（`proposal-coordinator/short-direct-write.ts`），整篇替换。
- 长篇：`long-project-store/operations.ts` 的 `replace` 写入不带 `expectedSha256`，同样整篇替换。

现在没出事，是因为短篇运行期间整本锁死；直接去掉锁，用户运行期间写的内容会被智能体整篇覆盖。长篇今天就有这个窗口：提案生成后、接受前，用户改了同一章，接受时会被静默覆盖。

### 2.3 已有的可复用机制

- Core `saveDocument` 已支持按文档的内容版本校验：传 `baseRevision`、不传 `force` 时，内容不符抛 `FolderCatalogConflictError`（`catalog.conflict`）。
- 项目事务层已支持 `expectedSha256`，提交时比对文件实际哈希。
- 长篇 `tool-edit` 修改前会读最新内容，与智能体读取时的“证据”比对，不一致就要求重读。
- 短篇工具只读发送时的快照（`session.prompt` 携带的 `shortWorkspace`），看不到运行中的修改。
- 提案已记录基线：短篇 `baseRevision`（内容版本），长篇 `beforeText`。
- `contracts/device-sync/merge-text.ts` 的 `mergeSyncText(base, local, remote)` 已实现按行三方合并，二期复用。

## 3 已确认的决定

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | 编辑不再因运行或待审而锁 | 悲观锁改为乐观并发：编辑随时可写，冲突在接受提案时按文档发现 |
| 2 | 冲突交给用户选 | 一期两种选择：保留我的（放弃这条提案）、用智能体版本覆盖（可撤销） |
| 3 | 自动审批遇到基线不符就暂停 | 这一条转为手动待审，提示一次；不自动合并，也不在用户光标下替换正文 |
| 4 | 结构操作维持现状 | 运行中增删、移动、重命名小节或章节仍然拦截；本期只放开文本编辑 |
| 5 | Core 是最终裁判 | Renderer 的预判只用于界面；落盘时 Core 按基线校验，防止检查与写入之间的竞态 |

## 4 方案总览

```
智能体读取（基线 B）── 生成提案（B → 智能体版本 A）
                    │
用户编辑（当前 C）──┤
                    ▼
接受时比较 C 与 B ── C = B ──→ 照常落盘（Core 再按 B 校验）
                    └ C ≠ B ──→ 标记“你修改过”，等用户选择
                                 ├ 保留我的：提案记为拒绝
                                 └ 覆盖：以用户确认时看到的 C 为基线落盘 A
```

“覆盖”同样带基线，只是基线换成用户确认时看到的版本。用户看到提示后如果又改了，覆盖会再次被拦下并刷新提示，不会把后来的修改也覆盖掉。

## 5 短篇、剧本

### 5.1 编辑解锁

- `editorLocked` 不再看 `documentHasWriteBarrier`。只在两种情况下短暂只读：正在落盘的那一篇（`acceptingDocumentIds`），以及同一本书正在接受结构类提案（只设置了书级标记、没有任何文档级标记）。文本提案落盘时，同书其他文档照常可写。
- 编辑器只读提示里删除“请先接受或拒绝待审修改”这一项。
- 自动保存和“全部排版”不再看运行状态；同一本书有提案正在落盘时仍延后保存（`acceptingWorkspaceIds`），以免和 Core 的整本 `projectRevision` 校验冲突。
- 结构协调器（`useShortWorkspaceStructureCoordinator`）仍用 `agentRunScopeHasWriteBarrier`，保持不变。

### 5.2 基线判定

接受时用户的“当前版本”取实时文档（`liveWorkspaceDocuments`，含未保存草稿）。当前版本满足以下任一条件就照常接受：

- 等于提案的 `baseRevision`：智能体读到的就是它。
- 等于最近一次被接受的智能体写入（协调器按文档记录）：基线只被其他智能体移动过。并行子智能体各自基于发送时的快照整篇写入，原有的“后写入者覆盖”顺序保持不变，不会因此打扰用户。
- 等于 `staleBase.currentRevision`：用户已确认覆盖这个版本（见 5.4）。

都不满足，说明智能体读取后用户改过：不写盘，在提案上记录 `staleBase`，重新计算差异（当前 → 智能体版本），状态保持 `pending`、审批模式改为手动。

提案到达时也做同样判定，所以智能体修改前用户就已改过的文档，卡片一出现就带提示。例外：基线取自尚未落盘的前一代提案时，到接受时再判定（前一代落盘后自然一致）。

只有智能体写入正文的接受路径记录“最近写入”；重命名等保留正文的结构写入不记录，否则会把用户已保存的修改误当作智能体写入。

### 5.3 落盘

文本提案改用 `shortAgentCheckedDocumentWrite`：传 `baseRevision = rev(本窗口所见的磁盘内容)`，不传 `force`，也不传整本的 `baseProjectRevision`。Core 只校验这一篇的内容版本，同书其他文档的保存不会冲突；内容未加载到本地（不可能有用户草稿）时不带校验，与原来一致。重命名这类只改标题的结构写入仍保留 `shortAgentDirectDocumentWrite`（`preserveCurrentContent`）。

Core 返回 `catalog.conflict`（检查和写入之间被改）时，刷新目录后同样标记 `staleBase`，不再进入终态 `conflict`。

### 5.4 覆盖

卡片带 `staleBase` 时，接受按钮变为“用智能体版本覆盖”。点击后：

1. `rev(当前)` 必须等于 `staleBase.currentRevision`；不等说明用户又改了，刷新提示并停止。
2. 写入前把 `discardSnapshot.beforeText` 设为用户当前版本。接受后的“撤销”会恢复用户的版本，所以覆盖可以撤销，用普通主按钮而不是红色危险按钮。
3. 以磁盘版本为基线落盘，记录 `staleBase.resolution = "overwrote"`。

“保留我的”即拒绝，记录 `resolution = "kept-user"`。同一车道后续的智能体修改沿用现有规则，被阻断。

### 5.5 自动审批

- 基线不符：从队列移除，审批模式改为 `request-approval`，提示一次“智能体运行期间你修改了《X》，这条修改已暂停，请选择保留或覆盖”。恢复会话时不会被 `resumeRecoveredAutomaticAgentEdits` 重新排队。
- 同一本书正有用户保存：以前自动审批直接记为 `error`；现在改为 `pending` 延后，用户保存全部结束后（`savingDocumentIds` 为空）重新调度。编辑解锁后两者撞车会很常见，不能让自动审批随机失败。

## 6 长篇

### 6.1 基线随写入下发

- 契约：`LongDocumentWriteProposalSchema` 的 `replace` / `append` 分支增加可选 `expectedSha256`（64 位小写十六进制），表示“智能体读到的正文”的 UTF-8 SHA-256。
- 智能体：`formLongProposal` 为 `replace` 写入填 `expectedSha256 = sha256(beforeText)`。所有非新建的改动都来自 `tool-edit`，`beforeText` 就是修改前读到的最新内容（含本轮未落盘提案的叠加）。
- Core：`applyOperations` 对带 `expectedSha256` 的写入，比较 `sha256(当前正文)`；不符抛 `LongWorkspaceOperationError("document_changed")`，`details` 带 `fileId`、`actualSha256`。事务操作同时带上读取时的磁盘哈希，堵住读取到提交之间的竞态。
- 错误码经 Core 映射为 `long.operation.document_changed`，Renderer 用 `getErrorPayload` 读取 `details`。

链式提案（同一章第二代）以前一代的智能体版本为基线，前一代落盘后哈希一致，不会误报。

### 6.2 Renderer

章节正文、人物文件、世界观文件三类卡片收到 `document_changed` 后，标记 `staleBase`（`currentSha256ByFileId` 记录 Core 报告的实际哈希），状态回到 `pending`、审批改为手动。覆盖时把这些哈希写回批次的 `expectedSha256` 再提交；磁盘又变了就再次拦下并更新哈希。

接受前仍先保存当前编辑器（`saveActiveLongEditorChanges`），所以未保存的修改也会被基线校验发现。

长篇其余写入路径（连续性文件、台账等）同样受 Core 校验保护，冲突时报明确错误、不会静默覆盖；它们的“覆盖”入口放二期。

## 7 界面

提案卡片带 `staleBase` 且待审时：

- 状态标签：“你修改过”。
- 说明：“智能体读取后你修改过这篇。覆盖会用智能体版本替换你的修改（之后可以撤销）；保留则放弃这条修改。”长篇说明不提撤销。
- 按钮：“保留我的”（拒绝）、“用智能体版本覆盖”（接受）。自动审批的卡片在这种状态下也显示按钮。
- 差异（短篇）：显示“当前 → 智能体版本”，即覆盖的实际效果。

提示一律用 toast，不在表单或卡片之间插入临时文案，保持布局稳定。

## 8 智能体侧

- 结算回传：带 `staleBase` 的提案，结算明细补一句：保留时“用户在你修改期间编辑了该文档，选择保留自己的版本”，覆盖时“用户在你修改期间编辑过该文档，确认采用你的版本”。下一轮智能体据此判断正文现状。
- 长篇 `tool-edit` 发现证据与最新内容不一致时，提示改为“该文档在你读取后已有改动（可能是用户正在编辑），请先完整读取最新内容再修改”，避免模型误以为是自己的错误。
- 短篇仍基于发送时的快照工作；下一轮发送会带上最新正文。

## 9 二期

- 三方合并：用 `mergeSyncText(基线, 当前, 智能体版本)`。短篇在提案到达时基线一致的情况下，`discardSnapshot.beforeText` 就是基线正文，可以直接合并；无重叠时给出“合并后接受”，有重叠时逐段选择。
- 长篇卡片显示“当前 → 智能体版本”差异；接受提案时的整本短暂锁收窄到目标文档。
- 连续性、台账等长篇写入的覆盖入口。
- 短篇工具在修改前经 Core 只读桥核对最新版本，与长篇对齐。
- 结构操作在运行中放开（需要处理提案目标被删除、移动的情况）。

## 10 验证

- 单元：基线判定与差异重算；`staleBase` 持久化解析；结算明细；契约的 `expectedSha256` 校验；`formLongProposal` 下发哈希；Core 在哈希不符时拒绝写入、在一致时正常写入；编辑锁只覆盖正在落盘的文档。
- 回归：运行 `pnpm typecheck`、`pnpm lint`、相关 `vitest`，以及 `pnpm lint:boundary`。
- 桌面实机：短篇让智能体改第一节、同时编辑第二节并自动保存；再在同一节上制造冲突，分别验证保留、覆盖、撤销；长篇同理验证章节正文。当前环境若无法启动 Electron，须如实说明未验证。
