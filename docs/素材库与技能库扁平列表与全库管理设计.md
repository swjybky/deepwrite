# 素材库与技能库：扁平列表与全库管理设计

2026-11-08 设计确认并补充。范围：左侧列表扁平化、全领域智能体管理、三个结构管理工具、库与分组长按排序，以及带“未绑定”标签的零散条目。第一至七节保留设计要求；第八节记录本轮实现与验证边界。

## 一、左侧列表

### 现状

`renderer/src/data/catalogWorkspace.ts` 的 `projectCatalogWorkspace`：技能库、素材库两个分区的节点为 `诊断节点 + 分组节点 + 类型分类节点`。未分组的库挂在 `createMaterialKindNode` / `skill-kind` 分类节点（`catalogNodeType: "category"`，带数量徽标）下面；分组内部已经是“库 + `categoryTag` 类型标签”的扁平结构。

### 目标

- 分区根节点改为 `诊断节点 + 分组节点 + 未分组的库`，删除 `material-kind` / `skill-kind` 分类节点及 `createMaterialKindNode`、`MATERIAL_TREE_KIND_ORDER` 中只为分类节点服务的部分。
- 未分组的库直接作为根节点，与分组成员一样带 `categoryTag`：
  - 技能库用 `SKILL_KIND_TAG_LABELS[library.skillKind]`（通用 / 情节 / 文风 / 其他）。
  - 素材库用 `MATERIAL_TREE_KIND_LABELS[library.materialKind]`；`mixed` 用“综合”（复用 `catalogWorkspace.general`，不新增语言键能复用就复用）。
- 首次展示的默认顺序：分组在前，未分组库按 `snapshot` 原有顺序，不再按类型聚类；用户排序后按持久化顺序展示，分组和未分组库可混排（见第四节）。
- 分组内成员、库内条目保持现状（扁平 + 标签），不做树形类型层级。
- 库节点仍保留 `materialKind` / `skillKind` / `workspaceType` 等字段，右键菜单、创建、移动、导出等依赖这些字段的功能不受影响。
- 检查依赖分类节点 id（`catalog:material-kind:*`、`catalog:skill-kind:*`）的展开状态持久化、默认展开、测试快照，统一改掉；旧的展开状态 id 失效即可，不需迁移。

## 二、素材库 / 技能库智能体

### 现状

- Renderer `utils/libraryAgentContext.ts` 的 `buildLibraryAgentWorkspaceContext` 为当前选中库生成 `LibraryAgentWorkspaceSnapshot`：当前库全文（受 128 条、32 万字上限），若属于分组再预填同组成员条目，`readableLibraries` 最多 8 个。
- contracts `library-agent.ts` 强制：非当前库条目必须 `readOnly`。
- Agent 工具（`pi-runtime-adapter/src/library-agent-tools/`）只能在 `workspace.libraryId` 中创建、编辑条目和改库介绍；系统提示词 `prompts-system.ts` 的【DeepWrite 当前资料库工具边界】写明“不得写入其它库”。
- 对话键与运行范围按库区分：`agentConversationKeyForDocument` / `agentRunScopeForDocument` 返回 `library:${domain}:${libraryId}`，Agent 端 `conversation-agent-rebuild.ts` 同样按库缓存。
- 提案落盘 `proposal-coordinator/library-lane.ts`、`library-staging.ts` 已按事件里的 `libraryId` 通用处理，不依赖“当前库”。

### 目标语义

- **范围：**素材库智能体管理用户全部素材库，技能库智能体管理用户全部技能库（内置技能库仍只读）。不跨领域：素材智能体不写技能库，反之亦然。
- **当前位置：**左侧选中的库 / 条目只作为上下文注入的焦点（【当前位置】：库名、id、标签、分组、当前条目），默认操作对象是它；用户提到其它库或需求明显指向其它库时，智能体可以直接读写其它库，无需用户先切换。
- **对话连续：**同一领域只有一个对话。左侧在同领域内切换库，对话不重置，下一轮发送时注入新的【当前位置】。
- 创作空间里按作品绑定范围工作的“资料库管理子智能体”（`library-management-runtime.ts`、`LibraryManagementScope`）**不在本次范围内**，保持只管理作品绑定库。

### 契约（`packages/contracts`）

1. `LibraryAgentReadableLibrarySchema` 扩展为全库索引项：`libraryId`、`title`、`kind`、`readOnly`、`entryCount`、可选 `groupTitle`。`readableLibraries` 上限从 8 提到与目录规模一致的值（如 512），语义改为“本领域全部可管理的库”，当前库必须在其中。
2. 删除“非当前库条目必须只读”的 refine；条目 `readOnly` 等于所属库是否只读。保留“条目所属库必须在索引中”的校验。
3. 新增 Core 只读命令 `catalog.readLibraryAgentLibrary`（名称可调整）：输入 `{ domain, libraryId }`，返回该库的 `LibraryAgentWorkspaceSnapshot`（不含其它库条目，无 `readableLibraries` 或只含自身）。快照构建复用 `utilities/library-management-service.ts` 里 `query` 的读取逻辑，抽出共享函数，不复制。
4. Main 在接受带 `libraryWorkspace` 的 `session.prompt` 时，在 activeRun 上记录 `libraryAgentScope: { domain }`；`internal-command-authorizer.ts` 对新命令校验：run 已接受、`parentRequestId === promptRequestId`、session 一致、`domain` 与 scope 一致。Core 侧再次校验库存在、领域正确。按 AGENTS.md 同步 contracts → Main 路由 → `core-entry.ts`。
5. `externalResourceIds`：库智能体运行占用本领域全部可写库（取 `readableLibraries` 中非只读项），外部控制写这些库时返回 `external.busy`。

### Renderer

- `buildLibraryAgentWorkspaceContext`：当前库预填规则不变（含当前条目必须来自 live 文档）；同组成员仍按剩余预算预填，但不再强制只读；`readableLibraries` 改为本领域全部库索引，当前库排第一。
- `agentConversationKeyForDocument` / `agentRunScopeForDocument`：库文档改为 `library:${domain}`。检查对话持久化、双端同步对话记录对 key 格式的 schema 约束，确认新 key 合法；旧的按库对话不迁移（磁盘上保留，界面不再显示），在总结里说明。
- 运行中同领域切换库：运行占用的是领域范围，切换不能打断或串改正在运行的那轮；下一轮再注入新焦点。
- 提案落盘：确认编辑非当前库条目时，`stageLibraryEditProposal` 能在 `liveWorkspaceDocuments` 找到目标文档；条目正文是按需加载（`catalogContentLoaded: false`）的情况下，先走现有加载入口取正文再比对 revision，避免误判冲突。
- 欢迎语 `data/agentWelcome.ts`、设置页 `LibraryAgentSettingsPanel` 描述文案改为“管理全部素材库 / 技能库”。

### Agent（`pi-runtime-adapter`）

- `agent-run-input.ts`：有 `libraryAgentProfile` 时注入 `libraryAgentCommandExecutor`（复用 `createCoreCommandExecutor`）。
- 工具状态改为按库的 Map（参照 `library-management-runtime.ts` 的 `states` + `reconcileLibraryToolState`）：预填的库直接建状态；其它库在首次访问时经新命令读取并缓存，本轮内复用。
- 工具参数：
  - `list_* / read_* / search_*`：可选 `library_id`，缺省为当前库；`search` 缺省搜索已加载的库，指定 `library_id` 时按需加载该库。
  - `create_*_entry`、`edit_*_entry`、`edit_*_library_overview`：可选 `library_id`，缺省为当前库。编辑仍要求本轮先读过该条目（沿用 `accessedEntryIds`）；只读库拒绝并给出明确原因；`baseProjectRevision` 取自该库快照。
  - 不在索引中的 `library_id` 报“库不存在或不属于本领域”。
- 系统提示词：`prompts-system.ts` 的工具边界改为“可管理本领域全部库；【当前位置】是用户正在看的库，默认指向它；写入其它库时在回复中写明库名”。加入全库索引（名称、id、标签、条目数、分组、只读），过长时截断并提示用 `list_*` 查看。内置默认提示词 `library-agent-defaults` 中“只管当前库”的表述同步修改。档案提示词仍由用户编辑，运行边界不可编辑。
- `conversation-agent-rebuild.ts`：对话缓存键改为 `library:${domain}`，每轮更新快照与焦点，不因切换库重建对话。
- Faux 本地响应（`faux-local.ts`）若依赖旧边界文本，同步更新。

## 三、智能体结构管理工具

### 工具划分

只新增三个工具，两个领域共用实现，领域由 Main 授权的运行上下文决定，模型不能通过参数切换领域。库、分组、条目使用稳定 id 定位，名称只作展示；同名时先查询确认目标。

| 工具 | 操作 | 职责边界 |
| --- | --- | --- |
| `manage_library` | `create`、`rename`、`reorder`、`delete` | 管理库本身；简介仍使用现有简介编辑工具 |
| `manage_group` | `create`、`rename`、`set_members`、`reorder`、`dissolve`、`delete` | 管理分组和成员库关系；不直接编辑成员库正文 |
| `organize_entries` | `move`、`reorder`、`delete` | 整理一个或多个条目；移动目标为正式库或未绑定区 |

- 现有 `create_*_entry` 支持创建未绑定条目；条目改名、正文编辑仍复用 `edit_*_entry`，不另增重命名工具。
- 扩展现有列表工具的查询范围，支持库、分组、成员关系、未绑定条目、只读状态、当前顺序及版本；结果分页并按需读正文，不把所有条目全文塞入提示词。
- 查询与创建使用显式的 `unbound` 目标类型；省略目标仍表示当前位置，不能把参数遗漏解释为未绑定。
- 每个工具接收有界的操作列表，各操作按 `action` 使用严格的判别联合 schema，只接受对应字段。批次上限由 contracts 统一规定；超限返回可拆分提示。
- 排序使用“目标 id + 同级锚点 id + 前/后位置”，避免模型重传整个目录覆盖并发新增项；库和分组排序调用同一个 Core 排序入口。
- 工具返回的是待审阅操作及摘要，不能在提案尚未接受时报告“已完成”。同一轮的操作进入同一份整理提案；新建对象使用提案内临时引用，Core 统一解析依赖，允许先建库再移入条目。
- 全领域入口能管理本领域未绑定条目。创作空间中按作品绑定范围运行的资料库管理子智能体暂不挂载这三个新增工具，也不因共享工具实现而扩大权限。

### 解散、删除与移动

- **解散分组：**解除分组关系，成员库和正文全部保留；成员库按原组内顺序插入原分组所在位置。解散是普通操作，不使用表示删除持久内容的红色按钮。
- **删除库：**从活动列表移除，保留可恢复的文件与注册信息；不提供永久擦除工具。
- **删除分组：**必须明确指定只移除分组还是连成员库一起移除，不能默认级联。前者的成员保留规则与解散一致；后者展示成员库和条目数量，并检查共享成员与作品引用，不能隐式删除其它分组仍使用的库。
- **删除条目：**删除活动库中的条目及其正文文件，不保留回收记录，无法恢复。
- **移回未绑定区：**保留正文及条目身份，仅改变归属，不等同于删除。
- 分组继续沿用现有按类别设置成员位置的模型；第一版不变成任意嵌套文件夹。成员类型不兼容或位置已占用时明确反馈，不能静默替换。

### 提案、授权与执行

1. 复用现有 proposal 生命周期，新增结构变更载荷，展示名称前后、来源与去向、顺序变化、涉及条目数和引用影响；正文修改仍显示正文差异。有关联的多项操作作为一个可接受单元，不能接受其中一步后破坏依赖。
2. 用户接受后，Renderer coordinator 经专用 Preload API、Main 路由交给 Core。Main 重新校验领域、操作范围和只读状态，Core 校验全部涉及项目、正文和目录顺序的版本；工具不提供 `force`。
3. 正式库、未绑定区、分组、排序注册表都纳入资源占用检查；新建对象也必须检查领域结构资源，不能只锁运行开始时已有的库 id。授权信息由 Main 权威解析，不能只信任 Renderer 传入的索引。
4. Core 复用现有事务机制。跨库移动、分组操作和批量整理须具备失败恢复与幂等回执；提交前先验证整个接受单元。落盘中断后从事务日志恢复，不能留下两个活动副本或两边都没有条目，也不能重试时重复新建。
5. 已编辑但未保存的条目先走现有保存协调流程；与待审阅正文提案冲突的移动或删除须先解决冲突。版本变化后刷新并重新审阅，不能自动覆盖。
6. 删除的风险确认整合在提案审阅中；手动删除复用删除确认界面。成功与错误使用 toast，不在列表或表单中插入临时提示。

## 四、库与分组长按排序

- 素材、技能分别保存顺序；分区根层允许分组和未分组库混排，组内成员也能在现有合法成员范围内排序。跨层移动和改变分组归属使用明确的菜单操作，第一版拖动只排序。
- 长按名称行约 350 毫秒进入拖动，期间保留少量位移容差；普通点击仍打开，滚动、提前松手、失焦或 Escape 取消拖动。按钮、展开图标和编辑框不触发拖动，拖动结束不再误触一次打开。
- 拖动时显示同级插入线，必要时边缘自动滚动；松手保存，取消则恢复原顺序。分组整体移动保留成员及展开状态。
- 右键菜单补充“上移、下移”，在首尾禁用对应项，提供无需长按拖动的操作方式。
- Renderer 先更新局部顺序，再用 Core 快照收敛；失败恢复权威顺序并 toast 提示，不使用页面级 pending 禁用整页。
- 复用 `useCreationResourceOrder` 的顺序协调思路和现有树节点交互，但资料库排序由 Core 在现有目录注册表中持久化；不复制创作列表仅存 localStorage 的方案，保证界面与智能体读取同一顺序。
- 注册表增加有版本的分领域根节点顺序、组内成员顺序。旧数据缺失时使用第一节的默认顺序；新增节点追加，删除节点清理，未知或重复 id 规范化。已有顺序不能因刷新、搜索或折叠而重置；筛选搜索结果期间禁用拖动，避免隐藏项的位置含义不明。

## 五、未绑定素材与技能

### 界面语义

- “未绑定”专指尚未加入正式素材库或技能库，与作品绑定状态无关；未加入分组的正式库不能标为未绑定。
- 素材页顶部“新增”主动作创建素材，技能页创建技能；菜单保留新建库、新建分组等入口。新增条目的“所属库”可选，默认“暂不放入库”；库内的新增入口默认当前库。
- 创建后直接打开正文编辑器。未绑定条目放在分区中独立的临时收纳区域，每条名称旁显示“未绑定”标签，空时隐藏该区域。它不参与正式库与分组的混合排序，内部条目可排序。
- 支持单条、多选后“移入库”，以及正式库内的“移回未绑定区”；移入后标签消失。目标使用现有 `PopupSelect` 和移动对话框，只展示合法、可写目标，继续检查作品类型、素材或技能类别及阶段兼容性。
- 未绑定内容可编辑、搜索、由领域智能体读取和整理；不自动绑定作品，不自动进入作品智能体上下文。需要用于作品时先归档并沿用现有绑定流程。
- 临时表示尚未整理，内容仍持久保存，重启后保留，不自动过期或清空。反馈、标签、拖动提示沿用主题变量，并支持深浅色、自定义强调色、紧凑窗口与字号变化。

### 存储、身份与引用

- 复用 `folder-catalog-store` 的清单、Markdown、版本、备份与事务能力，在应用数据目录下按领域及必要的作品类型懒创建内部收纳容器；不让每个零散条目成为一个新项目，也不建立平行存储服务。
- 内部容器通过显式用途字段识别，不能靠名称判断；UI 与智能体查询将其投影为未绑定条目集合，普通库选择、分组成员、作品绑定列表过滤内部容器。容器本身不能被改名、解散或作为正式库删除。
- 条目保持现有类别、阶段和作品类型约束；新建表单复用现有元数据选项，后续移动不得静默改类别或正文。收纳容器按兼容性分开存储，但界面可统一展示。
- contracts 新增明确的条目归属类型（正式库 / 未绑定），Core 解析真实存储位置；内部容器 id 不作为用户选择目标。编辑和提案仍携带可校验的真实项目、正文版本。
- 第二节的工作区快照进一步增加焦点类型：正式库、未绑定条目、领域首页。后两种不要求虚构一个当前正式库；没有任何正式库时也能打开领域对话、创建未绑定条目。对话键继续使用 `library:${domain}`，读取和写入的内部容器仍由 Main 授权。
- 移动保留稳定条目 id；目标存在同 id 时返回冲突，不能覆盖或偷偷重新编号。现有复合引用若包含 `libraryId`，移动时须更新引用并提供旧地址解析，或采用统一的稳定身份解析；实现前审计作品绑定、技能附件、会话、草稿、提案、搜索和导出入口，选择一条统一路径，不能只更新列表。
- 删除或移除库若影响作品引用，提案必须列明影响，不能留下无法解释的悬空引用。条目删除后无法恢复，确认文案与提案必须明确说明。
- 内部收纳容器纳入现有备份与恢复清单。导出入包不得将内部容器误识别成普通库；第一版沿用正式库导出入口，需要导出零散内容时先移入正式库。

## 六、实施顺序与范围

1. 保留第一、二节的扁平列表和全领域上下文改造；为新增结构操作补充 contracts、注册表兼容读取及 Main 权限模型。
2. 实现未绑定条目持久化、创建、编辑、搜索、归档和手动整理，验证移动、删除与已有引用。
3. 实现 Core 顺序持久化，接入长按拖动和菜单排序；复用已有分组管理和删除界面，统一解散与删除语义。
4. 挂载三个管理工具，接通结构提案、批量执行、冲突处理及 Faux 响应；使用与手动操作相同的 Core 服务。
5. 完成集成和桌面验收后再标记功能完成。

本次设计不包含素材、技能跨领域写入，任意嵌套分组，永久删除工具，或扩大创作空间资料库管理子智能体的范围。新增工具不自动开放为外部 MCP 工具。

## 七、验证

- 单元测试：
  - `catalogWorkspace` 投影：未分组库直接位于分区根节点并带正确标签；`mixed` 素材库显示“综合”；分组成员不变。
  - contracts：全库索引、可写的同组条目通过校验；条目所属库不在索引中仍被拒绝。
  - 工具：缺省写当前库；指定其它库时按需加载并产生带该 `libraryId` 的提案；内置技能库拒写；未读先改被拒；未知库报错。
  - 授权：新命令在 domain 不符、run 未接受、parentRequestId 不符时被拒。
  - Renderer：同领域切换库对话保持；编辑非当前库、正文未加载的条目时提案正常进入审阅而非冲突。
- 命令：相关包的 `pnpm typecheck`、`pnpm lint`、`pnpm test`（含 `disk-integration` 若涉及 Core 存储测试）、`pnpm lint:boundary`、语言数据预算检查。
- 桌面实机：需在沙盒外启动，本次由用户验收：左侧列表外观、跨库创建与编辑的提案审阅、切换库后对话连续。

### 新增功能验收

- 工具与提案：三个工具分别覆盖合法操作、非法字段、未知 id、只读目标、跨领域、过期版本及批次超限；未接受时无落盘，接受后批量结果一致；先建库再移动的临时引用能正确解析，拒绝或重试不产生残留与重复对象。
- 未绑定：首次创建、重启恢复、编辑与搜索、单条和批量归档、移回临时区、类型不兼容拒绝；空收纳区不显示，内部容器不出现在库和分组选择器中。旧版用户数据无需手动迁移即可打开。
- 引用与删除：移动后作品引用、技能附件和已加载文档仍能解析；脏草稿和待审阅提案不能丢失；解散保留成员，移除库保留文件、删除条目无法恢复，共享成员不会被隐式级联删除。
- 排序：根层库与分组混排、组内排序、上移下移边界、松手持久化、取消回滚、刷新和重启保持；新增删除后的顺序协调，以及两处并发修改导致的版本冲突。
- Core 集成：跨库事务在提交前、正文移动后、清单更新后和回执返回前中断，重启恢复后条目仍唯一存在；排序和未绑定内容随备份恢复。真实文件系统测试进入 `disk-integration`，涉及 Windows 文件语义的实现须通过原生 Windows CI。
- 桌面交互：短按只打开、长按排序、滚动不误触、拖后不误打开、Escape 与失焦取消、边缘滚动和菜单替代操作；逐帧检查无整页闪烁、列表跳高或错误中间态。检查主题、字号、窄窗口、弹层层级和 toast。
- 回归四项基础能力：创作空间绑定与引用、素材库编辑、技能库加载、设置页智能体权限；补充会话切换、条目删除、备份导出及外部资源占用检查。桌面启动沿用 `assertElectronLaunchAllowed()`，受沙盒拦截时不记为通过。


## 八、本轮实现记录（2026-11-08）

- 新增三个领域专用工具：`manage_library`、`manage_group`、`organize_entries`。已有创建工具用显式 `target=unbound` 创建零散条目。同轮结构操作合并成一份提案，接受后才由 Core 写入。作品绑定范围的资料库管理子智能体不挂载这三个工具。
- 顶部新增菜单可直接创建条目，所属库缺省为“暂不放入库”；按兼容类型复用内部容器，列表仅显示“未绑定”区域与条目标签。可批量移入库、移回未绑定区。完全空白的领域先通过新增条目进入编辑及领域对话。
- 库与分组支持 350 ms 长按同级排序及菜单上移、下移；顺序保存在 Core 注册表，保存后的快照更新局部列表，不使用页面级禁用。内部收纳区不参与正式库排序与绑定选择。
- 结构整理使用可恢复的跨项目事务、正文指纹、版本校验与幂等回执；手动条目移动、删除复用同一事务流程。移动保留条目 ID 并保存旧地址重定向；删除条目不保留回收副本。提案拒绝覆盖未保存正文，已成功提交不会因列表刷新失败变成“提交失败”。
- 工具中的“删除库 / 分组”只移出活动列表，文件保留，可通过打开已有库恢复；既有菜单中明确标为永久删除的操作继续沿用原确认流程。解散分组使用普通操作样式，工具的级联移除拒绝仍被其它分组共享的成员。
- 增加 Core 真实文件系统测试、工具和提案测试、Main 授权测试；桌面 `--library-groups-only` 覆盖两个领域的未绑定展示、长按排序、批量幂等、条目删除和既有分组删除，使用隔离数据目录。
- 当前验收平台为 macOS。原生 Windows 文件系统验收，以及所有主题、字号和紧凑窗口组合的视觉验收仍需在对应环境运行；不以本机类型检查代替这些验收。
