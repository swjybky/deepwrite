# R2 软件更新源

检查更新：`https://update.deepwrite.download/update.json`。
存储桶：`deepwrite-updates`，标准存储，亚太地区，最低 TLS 1.2。

现有 v1.8.5 的 18 个附件已完成云端同步与校验，根清单的 `feedUrl` 已指向 R2 版本目录。后续发布仍由同步工具在全部文件核验后切换版本指针。

发布文件放在 `releases/v版本号/`，文件名保持 electron-builder 的原始名称。安装包、blockmap 和平台清单全部上传并校验成功后，才更新根目录的 `update.json`。版本目录长期缓存；根清单使用 `Cache-Control: no-store`，并通过 ETag 条件写入防止并发覆盖。旧版本同步不会降低当前版本。

R2 只保留当前版本：上传前删除不属于当前版本或本次待上传版本的遗留目录；新版本校验和激活成功后立即删除其他版本目录。GitHub Release 历史附件继续保留。上传或激活失败时保留正在使用的版本，清理失败会令工作流失败，重跑后继续清理。所有发布通过同一串行工作流执行，避免并发上传与清理冲突。

每次上传前分页统计整个桶的对象大小，计入健康检查、根清单、残留上传和新旧版本同时存在的空间。预计峰值超过 10,000,000,000 字节（10 GB）时停止上传；仅差一个字节也会拦截。容量不够时不会先删除当前版本强行上传。这个限制由本发布脚本执行，不是 Cloudflare 的硬配额；其他程序直接写入及其他桶的用量需另行控制。

正常发布继续保留 GitHub Release。依照现有发布流程，附件完整公开后才更新主分支 `update.json`；这次推送自动触发 `sync-r2.yml`，从该版本的公开 Release 下载并校验附件，然后同步到 R2。R2 同步失败可以单独重跑该工作流，不必重新公开 GitHub Release。

同步现有正式版本：在 Actions 手动运行 `Sync an existing published release to R2`，输入与仓库 `update.json` 一致的标签。流程下载 GitHub 已发布附件，逐个核对 GitHub 记录的大小与 SHA-256，再上传 R2；不会重新构建或创建 Release。

上传权限为指定桶的 Object Read & Write。GitHub 仓库 Secret 名称：`DEEPWRITE_R2_PUBLISH_CONFIG`。JSON 字段为 `accountId`、`bucket`、`publicUrl`、`accessKeyId`、`secretAccessKey`；凭据只供发布工具使用，不放入 `DEEPWRITE_RELEASE_ENV` 或任何 `MAIN_VITE_*` 变量。

本机私密配置使用 Git 忽略的 `.env.r2`，文件权限为 600。已有经过校验的发布文件时，可在仓库根目录运行：

```sh
RELEASE_TAG=v版本号 node --env-file=.env.r2 tools/publish-r2-release.mjs upload 发布文件目录 update.json
RELEASE_TAG=v版本号 node --env-file=.env.r2 tools/publish-r2-release.mjs activate 发布文件目录 update.json
```

旧安装包内的检查地址不会随服务器配置改变，需升级到包含新检查地址的版本，或从新域名手动下载安装新版。R2 出站下载流量免费；存储和请求超出免费额度后按量计费，预算提醒不等于硬性停用额度。
