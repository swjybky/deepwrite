# 外部智能体控制接口设计

> 状态：第 2 节的决定已于 2026-10-31 确认，已实现 M0 到 M5，实现记录与验证见第 11 节。本文是实现依据；后续修改如需偏离，先改本文再改代码。

> 一句话：让 Claude、Codex、WorkBuddy 等外部智能体通过 MCP 操作运行中的 DeepWrite，帮用户管理创作空间、素材库、技能库和智能体团队。外部智能体直接做的文本操作不审批；它调用内置智能体干活时，强制自动审批，且用户必须已打开“跨阶段操作自动审批”。

## 1 背景与目标

DeepWrite 目前只能在界面里手动操作。用户希望直接对外部智能体说“把第三章复制一份”“新建一个素材条目”“让写作团队跑一下这本书”，由它去操作软件。

外部智能体不是另一支写作团队，而是软件的操作员。作品仍在 DeepWrite 里，写入仍由 Core 落盘，内置智能体仍用软件里配好的模型和团队。

项目现状：

- 没有 MCP、本地服务或自定义协议。`second-instance` 只把窗口显示出来，不解析参数（`apps/desktop/src/main/index.ts:2439`）。
- Renderer 的命令走 `main/index.ts` 里的 IPC 处理链，靠内联名单拦截内部命令，未被任何处理器接收的命令在链路末端抛错，默认拒绝。这套机制防的是可信的 Renderer，不能直接用于外部接口。`ipc/dispatch-command.ts` 和 `ipc/forbidden-commands.ts` 目前没有生产调用方。
- 自动审批、提案结算和对话编排都在 Renderer。对话控制器由 `conversationRuntimeRegistry` 按对话 key 管理，发送入口绑定当前打开的目标；`session.prompt` 的对话历史和 `workspaceContext` 也由 Renderer 组装。
- Core 写入后不发变更事件。Renderer 只在自身操作后和窗口聚焦时刷新。
- 删除是永久删除，没有回收站，也没有版本历史。

一期目标：

- **一套接入：** 同一个 MCP 服务和同一份 Skill 覆盖各家智能体，不为每家单独开发。
- **覆盖三个领域：** 创作空间、素材库与技能库、智能体团队管理。
- **两条执行路径：** 直接操作不审批；经内置智能体的操作强制自动审批。
- **用户看得见：** 外部操作的结果实时反映到界面，不需要重启或切换窗口。
- **不丢用户的字：** 不覆盖用户刚写的内容，误删可以恢复。

一期不做：

- 插件打包和插件市场上架；
- 独立 CLI（只保留桥接的诊断模式）；
- 模型配置、密钥、同步与备份的外部管理；
- 按路径导入导出、团队包导入导出；
- “更多功能”里的拆书、分析和聊天；
- 长篇人物、伏笔、账本等结构化数据的直接写入，以及长篇章节的增删和移动（`manage_document` 只支持短篇和剧本）；
- 库分组的删除和恢复；
- 文档局部替换（一期只支持整篇写入）；
- 软件未运行时直接读写作品文件夹；
- 远程访问，服务只面向本机。

## 2 设计决定（2026-10-31 已确认）

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | 外部智能体定位为软件操作员 | 一期范围是创作空间、素材库与技能库、智能体团队管理 |
| 2 | 操作的是运行中的软件 | 不直接读写作品文件夹；软件没开时由桥接拉起 |
| 3 | MCP 做接口，Skill 做说明书 | MCP 负责工具能力，Skill 负责工作流和规则；两者都安装 |
| 4 | 插件后放 | 插件只是分发格式，且每家不同；确有分发需要时再薄封装。一期先把 MCP 做好，Skill 随后补上 |
| 5 | stdio 桥接加本机端点 | 不开 HTTP 端口；桥接经 Unix socket 或 Windows 命名管道连到 Main |
| 6 | 对外用独立白名单 | 不一比一暴露内部命令，收敛为 24 个按任务设计的工具 |
| 7 | 直接操作不审批 | 文本的新建、写入、复制、移动、改名、删除直接执行，不走提案 |
| 8 | 经内置智能体的操作强制 `auto-approve` | 只对这次运行生效，不改用户全局的 `permissionMode` |
| 9 | “跨阶段操作自动审批”是运行前提 | 开关关闭时拒绝 `run_agent`，提示用户去设置打开；不替用户改设置 |
| 10 | 外部删除可恢复 | 不审批。小节、条目和智能体团队先存副本，保留 30 天；作品和库只移出列表，文件夹原地不动。用户手动删除的行为不变 |
| 11 | 写入必须通过版本校验 | 不审批也不覆盖用户新内容；外部永远不能使用 `force` |
| 12 | 外部接入默认关闭 | 用户在设置里打开总开关后才生效 |

决定 7 是 `AGENTS.md`“修改文稿须先展示 proposal 差异”的例外，M2 落地时同步更新该约定。

## 3 总体架构

```
Claude / Codex / WorkBuddy …
   │ MCP (stdio)            + Skill（工作流与规则）
   ▼
deepwrite-bridge            工具清单、转发、软件没开时拉起
   │ Unix socket / 命名管道 + 令牌
   ▼
Main：控制接口              开关、鉴权、白名单、审计
   ├─ 读取、团队管理 ───────→ supervisor → Core / 配置存储
   ├─ 直接写入 ─→ 窗口同一条命令链 → Core → 变更事件 → Renderer 刷新
   └─ 运行内置智能体 ───────→ Renderer 控制桥 → 现有发送入口与自动审批
```

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 契约 | `packages/contracts/src/external-control/` | 工具清单、输入输出 schema、错误码、Main 与 Renderer 之间的命令和事件 |
| 桥接 | `apps/desktop/src/extras/external-control/bridge-entry.ts` | MCP 服务、拉起软件、转发调用 |
| 控制接口 | `apps/desktop/src/extras/external-control/` | 本机端点、鉴权、工具路由、审计；由 Main 注册 |
| Core | `apps/desktop/src/utilities/` | 长篇条件写入、项目定位 |
| 回收区与审计 | `apps/desktop/src/extras/external-control/` | 由 Main 持有，存放在用户数据目录，不写入作品文件夹 |
| 控制桥（M4） | `apps/desktop/src/renderer/src/extras/external-control/` | 响应 Main 的请求：打开目标、发起运行 |
| 设置页 | Renderer `extras/external-control/` | 总开关、接入配置、回收区、操作记录 |

## 4 接入层

### 4.1 MCP 桥接

桥接是一个随安装包发布的脚本，用软件自身的二进制以 Node 模式运行，用户不需要安装 Node。项目已有同样做法：`storage-bootstrap.ts:45` 用 `ELECTRON_RUN_AS_NODE` 运行存储迁移入口。

这依赖 Electron 的 `runAsNode` 能力保持开启。以后如果配置 Electron Fuses，不能关闭它，否则桥接和存储迁移都会失效。

配置示例（Codex，路径以设置页实际生成为准）：

```toml
[mcp_servers.deepwrite]
command = "/Applications/DeepWrite.app/Contents/MacOS/DeepWrite"
args = ["/Applications/DeepWrite.app/Contents/Resources/app.asar/out/main/extras/external-control/bridge-entry.js"]
env = { ELECTRON_RUN_AS_NODE = "1" }
```

配置直接写可执行文件路径，不用 shim 脚本：Windows 上部分客户端不经 shell 启动，`.cmd` 无法运行。Linux AppImage 路径不稳定，设置页使用 `$APPIMAGE` 生成配置，路径变化时提示重新复制。

桥接的工作方式：

1. **启动：** 立即响应 MCP 握手和 `tools/list`。工具清单是随包发布的静态数据，不等软件启动。Codex 的 MCP 启动超时默认只有 10 秒，而软件冷启动可能更久。
2. **调用：** 读取端点文件，连接 Main，转发调用。
3. **拉起：** 端点文件不存在或进程已退出时，用去掉 `ELECTRON_RUN_AS_NODE` 的环境启动软件，并带上 `--external-control-launch` 参数，最多等 20 秒。软件已在运行时，这个参数经 `second-instance` 转给运行中的实例。
4. **启动时序：** 控制接口在窗口创建后才启动，这时 Core 已能响应，连接确认也有窗口可依附。
5. **总开关关闭：** 只靠“没有端点”无法区分“软件没开”和“开关没开”，桥接会白等 20 秒。所以收到拉起参数后，开关关闭的软件写一份 `status: "disabled"` 的状态文件，其中不含端点和令牌，桥接读到后立即返回 `external.disabled`。没有桥接来过时不写任何文件。
6. **失败：** 进程启动失败或被信号终止时立刻返回错误，不等到超时，让外部智能体请用户手动打开软件。
7. **退出：** 客户端关闭 stdin 后桥接立即退出，不留下孤儿进程。

工具 schema 用 Zod 编写，用 `z.toJSONSchema`（zod 4.4.3）生成。为兼容各家客户端，输入保持扁平结构，不用 `oneOf`，字段间约束在 Main 校验。

MCP SDK 用 `@modelcontextprotocol/sdk`（MIT），走 `pnpm-workspace.yaml` 的 catalog，作为 devDependency 由 electron-vite 打进 `out`，与项目其他依赖相同。桥接从 `@deepwrite/contracts/external-control` 子路径引入契约，不加载完整契约包，也不引用 `electron`。

### 4.2 Skill

Skill 名为 `deepwrite`，一份 `SKILL.md`，由设置页安装到各智能体的技能目录。内容只写工具 schema 表达不了的东西：

- 先调 `get_app_status` 了解软件状态；
- 写入前必须先读，写入时带回版本；遇到版本冲突要重读并重新生成内容，不能盲目重试；
- 什么时候自己操作，什么时候调内置智能体；
- `run_agent` 的前提、状态含义，以及如何把提问转给用户；
- 删除进回收区，以及如何恢复；
- 短篇、剧本、长篇在结构上的区别。

## 5 传输与安全

**端点：** macOS 和 Linux 用 `~/.deepwrite/control/control.sock`，Windows 用命名管道 `\\.\pipe\deepwrite-control-<用户哈希>`。不放在用户数据目录，因为该目录可被用户修改，桥接无从得知，而且 macOS 的 socket 路径长度有限。开发版用 `control-dev`，和正式版互不影响。目录权限 0700，socket 权限 0600。

**状态文件：** Main 启动控制接口时写 `control.json`，内容是端点、进程 ID、软件版本和令牌，权限 0600。令牌每次启动和每次重新打开开关时重新生成，退出时删除文件。崩溃留下的文件由桥接按进程是否存活判断，软件下次启动时清理。

**协议：** 桥接与 Main 之间用一行一条的 JSON。消息沿用项目的 Envelope，结果沿用 accepted/rejected 形状。首条消息 `externalControl.hello` 带令牌、客户端名称和协议版本，之后是 `externalControl.call`。这些类型不进 `CommandEnvelope`，Renderer 无法发送。认证前单条消息上限 4 KB，5 秒内未认证就断开；认证后上限 20 MB。

**授权：**

- 总开关默认关闭，位于“设置 → 外部智能体”。关闭时不创建端点，桥接返回 `external.disabled`。
- 某个客户端首次连接时，软件弹原生确认框，确认后写入用户数据目录的 `config/external-control.json`，以后不再询问。用原生框是因为它不依赖 Renderer 加载完成，也不占语言数据预算。客户端名称可被伪造，这一步用于防误接入，不作为安全边界。
- 弹窗未答复时，40 秒后返回 `external.approval_pending`，弹窗继续开着，用户确认后重试即可。同一客户端并发连接只弹一次。
- 用户拒绝后，这个客户端不再弹窗，直接返回 `external.unauthorized`，避免被反复打扰；关闭再打开总开关后恢复询问。拒绝不落盘。
- 同一用户下的本机进程本来就能读写作品文件，所以控制接口的安全边界是“不把能力扩大到其他用户和网络”，不防同用户的恶意程序。

**白名单：** 每个工具在 `tool-routes.ts` 有一条路由，只能调用路由里写明的命令。读取工具经 `supervisor.requestCommand` 访问 Core；写入工具走窗口同一条命令链（`routeExternalCommand`），工作目录解析、结果校验都和界面操作一致，不另写一份。`externalControl.locateProject` 是 Core 专用命令，已加入 `main/index.ts` 的内联拦截，Renderer 不能发送。

**输出白名单：** 工具结果用严格 schema 定义，未列出的内部字段会解析失败，不会流到外部智能体。Core 的错误信息可能带本地路径，一律不转发，只返回固定文案。

**凭据：** 任何工具的输出都不含 Provider 密钥和模型密钥。团队配置的 schema 里本来就没有凭据字段。

**审计：** 每次写操作记录时间、客户端、工具、目标 ID 和结果，不记录文本内容。保留最近 1000 条，设置页显示最近 50 条。

外部智能体读到的作品和素材内容可能夹带指令，这是提示词注入的入口。一期靠版本校验、回收区和审计兜底。

## 6 工具清单

共 24 个，M4 后全部开放。`manage_*` 用 `action` 参数合并同类操作，控制工具数量。

**状态与界面**

| 工具 | 作用 | 实现 |
| --- | --- | --- |
| `get_app_status` | 版本、窗口是否就绪、运行数、跨阶段开关状态 | Main |
| `open_in_app` | 在窗口里打开作品或库的第一篇文档，暂不支持指定文档 | Renderer 控制桥 |

**创作空间**

| 工具 | 作用 | 实现 |
| --- | --- | --- |
| `list_works` | 列出短篇、剧本、长篇 | `catalog.index`、`long.list` |
| `get_work` | 读取作品结构和文档列表，不含正文 | `catalog.index`、`long.getWorkspaceIndex` |
| `read_document` | 分页读文档，返回版本 | `catalog.readDocument`、`long.readDocument` |
| `search_text` | 在一部作品或一个库内搜索 | 长篇用 `long.search`；短篇、剧本和库按索引逐篇读取，到上限即停，不加载整个目录 |

**智能体团队**

| 工具 | 作用 | 实现 |
| --- | --- | --- |
| `list_agent_teams` | 列出团队；传 `teamId` 时返回该团队完整配置 | `AgentTeamConfigStore` |
| `save_agent_team` | 整份替换一个团队的配置，必须带版本 | `agentTeams.save` |

| --- | --- | --- |
| `list_trash` | 列出可恢复的内容 | Main 的回收区 |
| `restore_trash_item` | 恢复一项；小节和条目以新 ID 回到末尾 | 现有创建命令；作品和库走 `*.openAtPath` |

**内置智能体**

| 工具 | 作用 | 实现 |
| --- | --- | --- |
| `run_agent` | 发起运行，立即返回运行 ID | Renderer 控制桥 |

读取默认单次最多返回 12,000 字符，超出时返回 `nextOffset`。长篇已有分页字段，短篇和库按同样形式补齐。

只读工具标记 `readOnlyHint`。写入工具都不标 `destructiveHint`：写入有版本校验，删除可以恢复，而且 Codex 在 `approval: never` 下会直接拒绝标了这个提示的工具，与“直接操作不审批”冲突。其他外部智能体自身的工具授权由各家客户端决定，不受这里影响；Codex 的 `read-only` 沙盒下写工具会被它自己拦截。

## 7 直接操作

### 7.1 写入流程

以 `write_document` 为例：

1. **检查：** 总开关、令牌、参数；有内置智能体在运行时返回 `external.busy`。
2. **条件写入：** 带 `baseRevision` 走窗口同一条命令链，不使用 `force`。版本不符时返回 `external.stale_revision`，外部智能体要重读后基于最新内容再写。
3. **写后通知：** 成功后广播资源变更事件，Renderer 刷新。
4. **审计：** 记录客户端、工具和目标 ID，不记录正文。

原计划在写入前让 Renderer 保存编辑器内容，实现时取消了：用户关闭自动保存时，这等于替用户保存他还没决定保存的内容。改由版本校验和现有的保存冲突处理兜底。

### 7.2 版本校验

短篇、剧本和库条目用内容修订号：`catalog.saveDocument` 和 `catalog.saveLibraryEntry` 的 `baseRevision` 在外部工具里是必填的，Core 不符时返回 `catalog.conflict`。

长篇用索引里的文件时间戳。每次写入都会更新它，读写都在项目互斥区里，不需要算指纹。`long.writeDocument` 新增可选的 `expectedUpdatedAt`，不符时返回 `long.document_conflict`。比较必须在 `loadIndexedFile` 之前做，因为它会用磁盘 mtime 覆盖索引时间。这个字段只有外部路径传，现有内部调用不受影响。`long.writeDocument` 能写章节正文，只读账本等文件由 `assertDirectlyMutableDocument` 拒绝。

### 7.3 界面同步

新增事件 `externalControl.resource_changed`，载荷为 `domain`（work、library）和资源 ID，由 Main 广播。Renderer 收到后复用窗口聚焦时的刷新（`requestFocusRefresh`，自带节流），并刷新长篇列表。

用户有未保存内容时的行为（均已实测）：

| 情况 | 结果 |
| --- | --- |
| 短篇、剧本 | 外部写入成功，用户草稿保留，自动保存时弹“外部修改冲突”，由用户选择保留、重新加载或覆盖 |
| 长篇 | 长篇编辑器保存时没有版本校验，所以写入前先问窗口：有未保存内容时返回 `external.busy`，用户保存后外部重读再写，两边内容都保留 |

短篇在外部写入和用户保存之间的竞争靠冲突框兜底。长篇的询问和写入之间有极小的窗口，用户恰好此时开始打字，自动保存仍会覆盖外部写入。

### 7.4 删除与恢复

- **小节和条目：** 先由 Main 把内容存到用户数据目录的 `external-trash/<id>.json`，再走现有删除命令；删除失败时撤销副本。恢复时重新创建，ID 是新的，位置在末尾。保留 30 天，控制接口启动时清理。
- **智能体团队：** 和小节一样先存配置副本，保留 30 天。恢复时新建团队再写入配置，ID 是新的；原名已被占用时加“恢复”后缀；作品绑定不恢复。
- **作品和库：** 走现有的“移出列表”（`catalog.unregisterProject`、`long.unregister`），文件夹原地不动，回收记录只存路径。恢复时重新打开这个文件夹，所以 ID 和内容都不变，记录不过期。文件夹被用户移走时返回 `external.not_found`，记录保留。
- **路径安全：** 回收 ID 来自智能体，只有 UUID 格式才会拼成文件名。`list_trash` 不返回本地路径。

这样外部智能体没有任何途径真正删除一个项目文件夹。

### 7.5 与内置智能体的互斥

有任何内置智能体在运行时，所有写工具都返回 `external.busy`，读取不受影响。否则外部写入会让智能体的提案失去基线，自动写入随之暂停。这里用 Main 的 `activeRuns` 判断，范围比“同一目标”更大，偏保守但简单可靠。

## 8 运行内置智能体

### 8.1 前提检查

`run_agent` 在 Main 依次检查：

1. 窗口已就绪，否则返回 `external.not_ready`；
2. 常规设置里的“跨阶段操作自动审批”已打开，否则返回 `external.cross_stage_disabled`，Main 以缓存的通用设置为准，不替用户改设置；
3. 没有运行中的智能体，否则返回 `external.busy`，不抢占用户或其他外部智能体的运行。

运行开始后用户关闭跨阶段开关，不影响这次运行，因为设置已随 `session.prompt` 发出。

### 8.2 Main 到窗口的请求通道

运行只能在 Renderer 里发起，所以 M4 新增了反向通道：Main 广播事件 `externalControl.window_request`，窗口处理后通过 Preload 的 `externalControl.respond` 发回命令 `externalControl.window_response`，Main 按请求 ID 配对，40 秒没有回复返回 `external.not_ready`。请求种类是封闭的联合类型，只有 `open_target`、`start_run`、`run_status`、`answer_run`、`stop_run`、`long_editor_state`。

控制桥 `renderer/src/extras/external-control/useExternalControlBridge.ts` 是窗口一侧的唯一处理者。它回复前把结果转成纯数据，因为对话状态是 Vue 响应式代理，过不了 contextBridge；回复失败时补发一条错误，不让 Main 空等。

### 8.3 执行流程

1. 打开目标，复用资源树导航。界面会切到目标，用户能看到全过程。
2. 等待上下文稳定。长篇在报告就绪后还会短暂变化，发送预检发现变化就取消，所以要求就绪状态连续保持 1.5 秒，发不出去时再重试，最多 3 次。
3. 把消息放进输入框草稿，调用和发送按钮完全相同的入口，消息被取走后立刻把用户原来的草稿放回去。`session.prompt` 由现有链路组装，不另写一份。
4. 用控制器的 `overrideNextApprovalMode("auto-approve")` 让这一次发送自动审批。它只影响这一次，不碰用户的审批模式；发送预检会按文档偏好重设模式，所以不能用 `selectApprovalMode`。
5. 立刻返回运行 ID，工具调用默认 60 秒超时，写作运行通常更久。
6. 状态不做事件快照：`get_agent_run` 让控制桥当场读取对话的 `isBusy`、`pendingUserInput`、`messages` 和 `conversationError`。

模型、思考档位和团队模式沿用界面当前设置。传 `newConversation: true` 时新开对话，否则续接目标的当前对话。

### 8.4 运行状态

| 状态 | 含义 | 外部智能体该做什么 |
| --- | --- | --- |
| `running` | 运行中 | 过一会儿再查 |
| `waiting_for_input` | 智能体在提问或等抽卡选择 | 自己回答或转问用户，然后调 `answer_agent_question` |
| `waiting_for_user` | 有改动等用户处理，比如用户手动改了目标文本 | 告诉用户到软件里处理 |
| `completed` | 完成 | 读取回复和改动的文档 |
| `failed` | 失败 | 读取错误信息 |
| `stopped` | 已停止 | 结束 |

### 8.5 自动审批之外的等待

| 情况 | 来源 | 处理 |
| --- | --- | --- |
| 跨阶段写入 | `cross_stage_write` | 前提检查已保证开关打开，不会停 |
| 智能体提问 | `ask_user_question` | 转成 `waiting_for_input`，把问题和选项交给外部智能体 |
| 抽卡选择 | `subagent_draw` | 走同一条路径 |
| 用户改了目标文本 | 自动写入暂停 | 转成 `waiting_for_user`，只能在软件里解决 |

macOS arm64 实测结果：

| 验证项 | 结果 |
| --- | --- |
| 真实智能体 | Claude Code、dsh、Codex 都完成“发起运行、轮询、读回结果”，内容一致 |
| 提问转发 | `waiting_for_input` 带回问题和选项，回答后运行继续并完成 |
| 强制自动审批 | 用户设为手动审批时，外部运行的改动直接落盘，用户的 `permissionMode` 不变 |

实测发现并修复的问题：

- 智能体提问时，响应式代理过不了 contextBridge，错误被吞掉，查询一直等到超时。
- `selectApprovalMode` 会被发送预检覆盖，强制自动审批不生效，改为按次覆盖。
- 长篇打开后上下文还在变化，第一次发送被取消，改为等待稳定并重试。

这三处都只有用脚本化模型或手动审批配置才测得出来。

尚未验证：Windows；`subagent_draw` 和 `waiting_for_user` 只有单元测试和相同路径的实测；真实模型提供商。

### M5 接入体验（2026-11-01 完成）

设置页新增“外部智能体”分类，面板是 `renderer/src/extras/external-control/ExternalControlSettingsPanel.vue`，按需加载。总开关放在该面板顶部，与接入和管理集中配置。

- **接入配置：**按 Claude Code、Codex、DeepSeek Harness 和通用 JSON 切换显示，文本由 Main 按本机实际路径生成（`client-configs.ts`），Linux 的 AppImage 用 `$APPIMAGE`。优先给对方 CLI 的命令，不直接改第三方配置文件。
- **Skill：**正文是 `extras/external-control/skill/SKILL.md`，构建时内联。用户点击后写到 `~/.claude/skills/`、`~/.codex/skills/`、`~/.agents/skills/` 或 `~/.workbuddy/skills/` 下的 `deepwrite/SKILL.md`，只写这一个文件，目标由白名单决定。工作流规则放这里，工具描述保持简短。
- **管理：**查看并撤销已允许的智能体，撤销后下次调用重新弹窗；恢复回收站条目；清空回收站要模态确认，作品和库的文件夹不动，只是失去恢复入口；显示最近 50 条操作，只含时间、客户端、工具和结果。
- **命令：**`externalControl.overview`、`revokeClient`、`restoreTrash`、`emptyTrash`、`installSkill`，每个都返回最新概览。它们只从窗口进入，由 `handleSettingsCommand` 处理，不对应任何 MCP 工具，外部智能体不能撤销授权或清空回收站。

验收中发现并修复：短篇和剧本的 `genre` 是固定枚举，传错只得到笼统的“拒绝了这次操作”；现在工具描述列出可选值，错误信息也会列出。

验证（macOS arm64，临时配置和临时主目录）：真实窗口里安装 Skill、撤销、恢复、清空都生效，浅色、深色和 900×620 窗口没有横向溢出和控制台错误；面板显示的 `claude mcp add` 和 `codex mcp add` 原样运行成功，`claude mcp list` 显示 Connected。

安装包（`electron-builder --mac dir --arm64`，ad-hoc 签名）里也走通了全流程：从 `app.asar` 启动桥接，新建作品、写入、删除，在设置页恢复和安装 Skill，再把面板给出的命令交给 `claude mcp add`，`claude mcp list` 显示 Connected。这也补上了 M2 之后没在安装包里验证过写入的缺口；安装包里的 `run_agent` 仍未验证。

验收时要隔离主目录：macOS 上 `app.getPath("home")` 不读 `HOME`，需同时设 `CFFIXED_USER_HOME`，否则 Skill 会写进真实主目录。

尚未验证：Windows 和 Linux 上的路径与命令引号；WorkBuddy 的 Skill 目录和 MCP 配置，这一项按其他客户端的约定推断；DeepSeek Harness 的 Skill 目录。

### M5 之后：团队模式与默认值（2026-11-01）

用户经 Codex 调 `run_agent` 时，输入框显示团队模式，这一轮却没有 `spawn_subagent`。根因是时序：窗口刚启动、这本书的会话第一次创建时，保存的运行设置要等异步恢复完历史才应用，`run_agent` 没等就发送了，读到的是初始值。之后设置恢复，输入框才显示团队模式。已打开过的书不受影响。技能库和素材库管理子智能体开启时普通模式也有 `spawn_subagent`，所以判断是否带上团队要看工具里有没有团队成员，不能只看工具名。

- `run_agent` 打开目标后先等 `conversationRuntimeRegistry.drain()`，再发送。
- `run_agent` 新增可选参数 `mode`。省略时有可用团队就走团队，否则走普通；`team` 在没有可用团队时报 `external.invalid_input`；`normal` 只用主智能体。按次覆盖（`overrideNextAgentTeamMode`），不改用户在输入框的选择，`get_agent_run` 返回实际模式。可用性和输入框用同一个判断（`resolveAgentTeamModeAvailability`）。
- 对话默认值改为团队模式和自动审批。没有保存过选择的书默认团队；已保存“普通”的书保持不变。全局默认审批仍以“设置 → 常规”为准。
- `AgentTeamModeSelect` 在团队目录重新加载时不再把模式切回普通。作品确实没有可用团队时仍切回普通并保存，之后启用团队要手动切回。

验证：用脚本化模型和带成员的团队，在真实窗口里检查请求中的工具定义：新书、窗口重载后未打开过的书、输入框选普通时都带上团队；`mode: "normal"` 不带；没有团队时默认走普通，显式 `team` 报错。

### 多作品并发与多步骤会话（2026-11-02）

- 外部基础修改、打开目标和启动交接按应用实例的短 FIFO 排队；只读查询、运行查询、回答和停止不受队列阻塞。排队超过8秒返回 `external.busy`，超时请求不会在之后执行。生成生命周期不持有队列。
- Main 根据被接受的 session.prompt 记录作品与可写资料库范围，外部修改只阻止重叠资源；缺少可信范围的运行仍保守互斥。创建新作品不受其他作品生成阻塞，团队全局变更与回收恢复沿用全局保护。
- Renderer 同样串行处理导航和发送，等待真实发送预检／接受完成再释放，不以草稿清空为接受标志。不同作品保留各自 controller，切到下一本书不会停掉上一部。
- run_agent 支持 sessionId 续接；返回快照携带 sessionId 和 workId/libraryId。新任务传 newConversation，同一作品的后续步骤传 sessionId，两者不能同时使用；同一作品生成时不允许直接改稿或切换会话。
- 内部主运行容量从4调为8，以容纳五部独立作品；更多功能分析上限仍为3，容量限制仍有效。
- 项目灵感通过短文件锁原子领取，先标记已领取，启动成功后改为已使用；每个外部线程只跟踪自己持有的 runId，不再等待其他作品的整轮生成。
- macOS 隔离配置的 `--external-concurrency-only` 桌面冒烟已通过：五个独立会话、生成期间创建、同会话续接、旧结果保留。受控并发单元测试另验证五个运行同时存活和停止隔离；Windows/Linux 未实机验证。
