# 任务：为本项目建立开发文档体系并整体梳理一遍

你是在这个仓库里工作的编程智能体。请通读项目，建立（或重构）一套给智能体用的开发文档：入口 `AGENTS.md`，加上按需加载的 `DESIGN.md` + `design/`、`TEST.md` + `test/`、`ERROR.md` + `error/`。完成后给我一份整体梳理。

**直接开始，不要先问我。**只有在不问就会做错且无法回退的地方才停下来问；其余情况选最合理的做法，把假设记下来，最后一起列出。

## 一、核心思路（所有文件都遵守）

1. **渐进加载。**`AGENTS.md` 是唯一常驻入口，只写行为准则、开发阶段和项目边界，其余文档用链接指过去。`DESIGN.md` / `TEST.md` / `ERROR.md` 是二级索引，各自目录里的条目只在命中时才读。每个索引都用“何时读 / 症状 / 改动区域 → 条目”的表格告诉智能体该读哪一条，不让它整目录加载。
2. **只写结论和做法。**这些文档都会进入上下文：不写背景故事、改动经过、泛泛的原则或教科书知识，只写本项目特有、照着就能做的规则。过时即删，不留历史。
3. **事实必须可核对。**文档里出现的命令、路径、文件名、函数名、类名、变量名、数值，都要在仓库里真实存在并亲自核对过；命令至少实际跑一次。查不到的不写，不靠猜补全。
4. **记录现状，不改代码。**本任务只动文档和必要的忽略配置。发现代码里的不一致、坏味道或缺陷，记录到最终梳理里，不顺手修。
5. **体积预算。**`AGENTS.md` 约 8 KB 以内；`TEST.md`、`DESIGN.md` 各约 4–6 KB；`ERROR.md` 约 3 KB；`error/` 每条 ≤ 25 行；`design/` 每个文件聚焦一类控件。超了就压缩或下沉到子目录。
6. **语言与风格**跟随项目现有文档（README、注释、提交信息）的主要语言；表格优先于长段落，规则用“**粗体关键词：**一句话”的形式。子目录里的每个文件第一行写 `返回 [XXX.md](../XXX.md)。`。

## 二、先调研（不写任何文件之前）

逐项弄清，并在心里列出“项目画像”：

- 项目类型、技术栈、语言、包管理器、monorepo 结构、进程/模块分层、入口文件。
- 已有文档：README、`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`CONTRIBUTING`、`docs/`、各级目录下的 README、skill 目录。**已有内容要迁移不丢失**，记下每条约束的去向。
- 构建、测试、lint、格式化、类型检查、打包脚本（`package.json` scripts、Makefile、CI 配置）；测试框架和分组；最快的“只测改动相关”命令是什么。
- 格式与规范配置：`.editorconfig`、prettier、eslint、ruff、gofmt 等；忽略文件。
- 是否有用户界面：样式入口、主题变量、设计 token、通用组件、布局骨架、图标库、多语言方案。
- 跨进程 / 跨服务边界、数据写入的唯一入口、密钥存放位置、不能上传的内容。
- 用 `git log` 浏览近几个月的提交（尤其 `fix`、`revert`、反复改同一处的提交），代码里的 workaround 注释、`HACK` / `FIXME`、平台分支（Windows/macOS）、预算类测试——这些是 `error/` 条目的来源。
- 能否在本机起测试环境（开发服务器、Electron、模拟器、浏览器预览），起不来的原因。

## 三、要产出的文件

### 1. `AGENTS.md`（入口）

开头一句说明“本文件是开发入口：行为准则、开发阶段与项目边界，其余文档按需加载”。按下列小节写：

- **开发阶段：**按改动大小自行判断做哪些阶段，简单改动直接改、最小验证、回复里说明即可。
  - 理解：看相关代码和设计文档，大功能先对齐方案或写设计稿（说明设计稿放哪）。
  - 预防：涉及 ERROR.md“按改动区域预读”中的区域时先读对应条目。
  - 实现：守住下方边界；改界面时读 DESIGN.md。
  - 验证：见 TEST.md；样式改动要截图比对，值得留档的写进 `test/`。
  - 排错：按 ERROR.md“按症状查找”加载条目；反复出现的错误沉淀为新条目。
  - 提交与发布：指向项目已有的提交/发布流程或 skill（没有就写最小规则）。
  - 末尾一句：“这些文档都会进入上下文：只写结论和做法，过时即删。”
- **行为准则：**照搬以下四条，按项目措辞微调：
  - 先想清楚：说明影响实现的假设与取舍；有多种理解时列出差异，关键问题先问；有更简单的方案就提出。
  - 简单优先：只写解决当前问题的必要代码，不加未要求的功能、配置、一次性抽象，也不处理不可能发生的错误。
  - 精准修改：每行改动都对应当前请求，遵循现有风格，不顺手改相邻代码、注释或格式。删除本次改动造成的无用代码；原有的无用代码只指出，不删。
  - 目标驱动：先定可验证的成功标准，验证通过才算完成；受阻时说明未完成项，不把未验证的结果报告为成功。
- **项目红线：**调研中发现的“绝不能做”的事（不能推送的分支、不能动的数据、不能进日志的东西）。没有就省略本节。
- **项目布局：**一张“位置 | 职责”表，覆盖主要目录和包；一句话说明新能力放进现有分层，不另建平行入口。
- **模块与协议边界：**跨进程/跨层只能怎么通信、谁是数据唯一写入者、密钥留在哪、改协议的顺序、改入口时要同步检查的配置。只写有代码依据的。
- **代码质量：**格式以哪些配置为准、只格式化改动文件；不设固定行数上限，文件明显承担多项职责时再按职责拆（约 600 行可作提醒）；默认不写注释，只写代码表达不了的“为什么”，一两句为限，不写复述代码的注释、改动经过、无归属 TODO、大段文件头。
- **敏感信息：**测试、夹具、快照、Mock、日志不得含真实地址、IP、生产域名或可用凭据（地址用 `example.test`，凭据用无效占位值）；发布凭据从哪来。

如果仓库用的工具读 `CLAUDE.md`，建立只含一行 `@AGENTS.md` 的 `CLAUDE.md`（已有内容先迁入 AGENTS.md）。

### 2. `DESIGN.md` + `design/`（有用户界面时）

`DESIGN.md` 写产品层面的约束与整体骨架，开头一张“文件 | 何时读”表指向 `design/`：

- **产品设计约束：**这个产品给谁用、什么是主角、视觉基调、哪些主流程、必须跟随的外观设置、最小窗口/屏幕尺寸与字号范围、反馈方式（toast vs 模态）、减少动效。从现有界面归纳，不凭空设定。
- **颜色：**主题变量来源（哪个文件哪个函数生成），“用途 | 变量 | 说明”表；规则：只用变量、需要混合怎么混、主操作色、红色/警告色的语义、阴影、需要检查的主题。
- **布局：**整体骨架用 ASCII 图画出（各栏宽度、变量名、响应断点、折叠方式），整页与弹窗的尺寸规则。
- **样式代码放哪里：**全局入口、拆分文件如何接入、组件样式作用域、全局类名前缀约定。

`design/` 按控件类别拆文件，常见：`tokens.md`（变量名、字号换算、间距圆角、z-index、动效时长）、`buttons.md`、`forms.md`、`dialogs.md`、`feedback.md`（toast、保存状态、加载、乐观更新、防闪烁）、`pages.md`、`icons.md`、`copy.md`（文案与多语言）。每个文件写：种类表（类名 | 外观 | 用途）、尺寸数值、选择规则、状态（disabled / focus / 进行中）、可访问性要求、参照组件。**数值全部从代码读出**；项目里同一控件有多种写法时，记录占多数的那种，并把不一致列进最终梳理。

没有界面的项目：跳过 DESIGN 和 `design/`，在 AGENTS.md 里不留链接；若有 CLI 输出、API 响应、错误码等对外约定，可改写成 `DESIGN.md` 的“接口约定”，同样按需拆子目录。

### 3. `TEST.md` + `test/`

开头一句：“本文件写验证思路与报告规范。每次验证的报告和产物放在 test/，并在文末验证记录登记。报错时转 ERROR.md。”

- **原则：**动手前把请求写成可观察的成功标准，完成后逐条核对，没核对的写进“未覆盖”；按影响面验证，默认不跑全量，修正中只重跑失败项；测可观察行为和失败路径（加校验先测无效输入，修缺陷先写能复现的失败测试，重构前后相关测试都要过）；类型检查和构建不能代替运行时、界面、安装包、真实依赖的验证，被环境拦下的记为“未验”并写明原因和需要谁补。
- **验证分级表：**L1 改动内（每次开发循环，只测相关文件 + 只 lint/格式检查改动文件，写出**实测可用**的命令）/ L2 影响面（改类型、协议、跨进程、界面、打包时，L1 + 下表加测）/ L3 全量（用户要求、大重构、依赖升级、发版前；平时交给 CI）。写明全量里哪些慢、为什么开发中不反复跑。
- **按改动加测表：**“改动 | 加测”，按本项目的实际风险列（schema、磁盘/数据库、跨进程入口、打包、平台差异、外部服务、智能体/提示词等），每行给命令或方法。
- **运行验证：**项目有 MCP、CLI、脚本或调试接口能驱动真实运行时，写清怎么用来验证、要记录哪些 id、跟踪到终态才算数。没有就省略。
- **视觉验证（有界面时，样式改动必做）：**① 起可重复的测试环境（探针脚本 / 开发服务器 / 浏览器预览，用临时数据，不碰真实用户数据）；② 动手前截基线，漏截时用 `git worktree` 检出 HEAD 补截，不 stash 共享工作区；③ 同条件截改后（尺寸、主题、字号、数据一致），至少浅色+深色，涉及布局加最小尺寸和最大字号，有状态变化加对应状态；④ 逐对比对裁切、溢出、换行、对齐、主题跟随，每对一句结论；⑤ 截图存 `test/日期-主题/`，命名 `before|after-light|dark-宽x高[-字号].png`，最后把对比图发给用户并附一句结论；⑥ 环境起不来记“未验”，不用类型检查代替。
- **环境约束：**临时 harness 放临时目录用完删；真实服务/模型/密钥能否用于测试、谁同意的；不在真实数据上跑写入；结束进程前先核对命令行；改了哪些代码后必须重启开发环境、重启顺序。只写本项目真实存在的约束。
- **报告规范：**功能开发、缺陷修复、样式改动和有产物的验证写报告，简单改动只在回复中说明；报告 `test/YYYY-MM-DD-主题.md`，产物放同名目录，同一任务多轮追加到同一份；≤ 40 行，五节：目标与成功标准 / 环境 / 步骤与命令（注明级别）/ 结果（通过、失败、未验）/ 未覆盖与后续；产物只放合成数据、采样和截图，不含私有内容、密钥、真实地址，单文件 ≤ 1 MB；写完在“验证记录”加一行，结论 ≤ 20 字，被取代的旧行删掉。
- **验证记录：**“日期 | 主题 | 结论 | 报告”表，先登记本次任务的报告。

同时把 `test/` 加进 lint、格式化、测试运行器的忽略配置，确认它不会被当成测试目录收集（若 `test/` 已被代码测试占用，改用 `verification/` 并全文统一）。

### 4. `ERROR.md` + `error/`

开头写两种用法，都只加载命中的条目：**开发前预防**（改动涉及下表区域先读，照“预防”做）；**出错时排查**（按步骤与症状表处理）。

- **按改动区域预读表：**“改动区域 | 预读条目”。
- **处理步骤：**① 留现场：完整报错、触发命令或操作、错误码、平台与版本；② 查表：按症状命中条目，未命中按最小复现排查；③ 先复现再修：写能失败的测试，修根因，不放宽上限、不调高预算、不 force、不绕过校验或沙盒，除非用户同意；④ 受阻即说明：两轮无进展，或根因在他人改动、外部服务、用户环境时，停下说明已知事实与选项；⑤ 沉淀：同类错误第二次出现或排查明显耗时，新建 `error/英文短名.md`，在两张表各登记一行。
- **按症状查找表：**“症状 / 关键词 | 条目”，症状写可搜索的原文报错或用户可见现象。
- **条目格式：**每条 ≤ 25 行，四节：**症状**（可搜索的原文报错）/ **根因** / **处理**（含关键文件与函数）/ **预防**（对应测试或检查）。

种子条目只来自真实证据：git 历史里修过不止一次的问题、代码里的 workaround、已有文档里的“坑”、预算/上限类测试、平台差异。**不编造**；证据不足就少写几条，宁缺毋滥。常见值得收的类别：环境/沙盒拦截、跨平台路径与换行、跨进程错误序列化、schema 新旧兼容、两处上限不一致、预算测试超限、界面闪烁与输入被锁、全局样式类名冲突、误杀进程、工作区混有他人改动。

## 四、收尾自查

1. 用脚本检查所有新建/改动文档里的相对链接都可达；`error/` 每个条目都在 ERROR.md 两张表中登记过、≤ 25 行；`design/` 每个文件都在 DESIGN.md 表中登记过。
2. 文档里出现的命令逐条实际执行过（至少 L1 命令）；路径与符号抽查存在。
3. 对已有文档做迁移核对：旧文件里每条约束在新体系里都有去处，删掉的只能是过时或重复内容。
4. 跑格式检查与 lint，确认 `test/` 产物不影响 `format`、`lint`、`test`。
5. 把本次过程写成 `test/YYYY-MM-DD-dev-doc-system.md`，按报告规范五节，并登记到 TEST.md。
6. 不提交、不推送，除非我要求。

## 五、最后给我的整体梳理

在回复里（不另建文件）按以下结构写，简洁、具体、带文件链接：

1. **项目画像：**一段话说清项目是什么、技术栈、分层、怎么跑、怎么测。
2. **新建与修改的文件：**清单 + 每个文件一句话用途 + 体积。
3. **关键约定摘要：**每个文档里最重要的 3–5 条，让我不打开文件也知道大意。
4. **旧内容去向：**原有文档的约束各迁到了哪里，删了什么、为什么。
5. **假设与待确认：**你替我做的决定，以及需要我拍板的问题（每条给出你的推荐）。
6. **发现的问题（未修改）：**代码或配置里的不一致、风险、缺失的测试、跑不通的命令，按严重程度排序。
7. **验证结果：**自查各项通过 / 失败 / 未验，未验写原因。
8. **建议后续：**最值得做的 3 件事。
