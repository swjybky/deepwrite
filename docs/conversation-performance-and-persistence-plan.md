**DeepWrite 长对话性能与持久化修复方案**

日期：2026-09-11。状态：核心修复已通过本机及 macOS arm64 测试包验收；尚未达到的资源目标和其他平台边界见实施记录。范围：长会话卡顿、会话记录超限后无法保存，以及缺少历史管理入口。

目标是让日常消息更新的开销取决于本次变化和当前可见内容，保证已确认保存的数据可以恢复，并保持现有智能体、审批和编辑功能。性能与兼容性必须通过实际验收，以下指标均为目标，不是已经达到的结果。

1. **已确认的问题与边界**

   修复前的 `RendererStateStore` 将全部记录写入 `renderer-state/conversation-persistence.json`。每个 key 的值上限为 64 MiB，整份文件上限为 256 MiB；一个作品下的多个会话共享同一个历史 key。保存超限会保留上一次成功的磁盘版本，新消息只留在内存；同一作品中新建会话不会释放旧历史。

   修复前的对话消息存在同步深度监听、全历史正文指纹拼接、全部消息及折叠详情挂载、滚动导航重复查询 DOM、全量快照序列化等问题。仅拆分文件或提高容量不足以解决这些问题。

   使用实际对话控制器的合成数据实验中，100 轮、每轮 120 行差异的约 11.92 MiB 数据，每次模拟流式更新两个字段耗时中位数为 58.86 ms；每轮 500 行差异的约 47.29 MiB 数据为 269.96 ms。该实验未包含 DOM、IPC、绘制和磁盘开销，后续应保留相同夹具进行比较。

2. **功能保留要求**

   保留普通聊天、短篇、剧本、长篇、资料库、学习仿写等现有会话入口及共享关系；保持会话 ID、消息 ID、时间、顺序、角色、草稿、模型设置、历史标题与预览语义。

   保留流式正文、思考过程、工具参数原文和解析结果、子智能体过程、失败重试、停止生成、用户输入请求；历史中的详情仍可展开查看。运行过程在当前产品中有可见功能，不能统称为无用遥测后自动删除。

   保留审批模式、待审批提案、提案代次与前置依赖、冲突检测、接受和拒绝、重试、定位文稿，以及已支持的撤销功能。`discardSnapshot`、版本校验和操作去重信息属于功能数据；不支持撤销的提案类型也不应因本次优化改变行为。

   保留历史消息修改重发、现有后续历史替换时机、消息复制、回复选区插入、轮次预览与跳转、滚动跟随和手动上滚锁定。长列表优化必须覆盖这些交互，不能只验证页面能显示。

   本次不改变模型输入内容、工具定义、Agent 缓存复用和恢复上下文的现行规则，不新增自动摘要或截断。UI 分页后，恢复模型历史必须独立查询完整持久化数据，再应用现行 80 条、单条 20,000 字符、总计 120,000 字符及过滤规则，不能把可见消息页直接当成模型上下文。

3. **存储选型与进程职责**

   在现有 Core Utility 中引入会话存储服务，采用 SQLite 按消息、文本块和运行实体存储；使用 Core 管理的专用工作线程执行数据库操作、压缩和解压。Renderer、Preload、Main 保持现有分工，Agent 不获得写盘能力，不增加新的 Utility 进程。

   当前本机 Electron 42.5.0 的运行时探测确认：Node 24.17.0 自带 `node:sqlite`，SQLite 为 3.53.0，内存数据库建表、写入和读取成功。该探测不等于已完成 Core Utility、工作线程及 Windows/macOS 安装包验证；这些是实施第一步的兼容性门槛。只使用该 Node 版本已有的 API。

   `DatabaseSync` 是同步接口，因此不能直接在 Renderer、Main 或承担其他项目命令的 Core 主事件循环执行长数据库操作。工作线程由 Core 管理生命周期、排队和错误恢复，并维持单写者约束。[Node 官方说明](https://nodejs.org/api/sqlite.html#class-databasesync)

   会话库位于应用本地数据目录。采用事务、外键、索引和 WAL；已保存状态以事务提交确认为准，使用可靠性优先的同步设置。短事务批量处理，整理和 checkpoint 分片调度，不放在输入或滚动路径。单独验证数据库备份时 WAL 的一致性，不能复制一个仍在写入的数据库主文件就宣称完成备份。[SQLite WAL 说明](https://sqlite.org/wal.html)

   SQLite 仍可能只有一个主要物理库文件，但日常操作只读写相关记录，不会对整个历史执行 JSON stringify、parse 或整文件替换。会话继续增长不再触发原来的 64/256 MiB 累计拒写；单请求和分块大小仍设上限，防止一次传输过大。物理磁盘不足仍必须准确报错。

4. **数据组织、去重与缓存**

   会话元数据保存所属作品、当前会话、时间、标题、预览、消息数和轮次索引；正文按消息及文本块保存。运行、处理步骤、工具调用、子智能体和提案分别保存稳定 ID、状态和关联引用，大文本通过内容引用加载。单条消息持续增长时也追加或修改尾部文本块，避免反复覆盖完整的大字符串。

   完成后的相同文本、重复提示词、Schema 和输入快照由 Core 按内容哈希复用；压缩发生在工作线程。原始工具参数与解析结果不等价时分别保留，不能用重新 stringify 的结果替代原文。正文和过程文字只有内容确实相同时才能共用存储，必须保留现有展示语义。

   流式数据先按块追加，完成后再执行低优先级整理和去重；不在每个 delta 上计算整个消息的哈希或重新压缩。详情加载响应有字节预算，特大详情分块读取，避免将数十 MiB 数据一次传回 Renderer。

   Renderer 只缓存当前窗口附近的消息和已展开详情。缓存按字节和条目数实行 LRU 淘汰；活动运行、正在编辑、已展开操作所需数据、未确认写入数据及待审批依赖不能被直接淘汰。其余历史可以卸载，再查看时从 Core 恢复。

   自动回收只针对派生缓存、可重建索引和已确认无引用的内容。会话正文、历史思考、工具详情及撤销依据默认完整保留，可以压缩、去重和冷加载，不按天数自动删除。共享内容只有在事务内确认所有引用均已解除后，才进入可取消、分批执行的回收队列。

5. **增量写入与保存状态**

   在现有 `@deepwrite/contracts` / Envelope 体系中增加明确的历史操作：分页列出会话、分页读取消息、查询轮次与模型恢复历史、读取详情块、提交变更批次、确认保存进度、导出、软删除和恢复。先定义 Zod Schema，再接入 Preload、Main 路由和 Core handler；不暴露 SQL、任意文件路径或未校验通道。

   每批写入携带会话 ID、运行或历史代次、唯一批次 ID、顺序号和预期版本；Core 在一个事务中应用正文变化、状态和索引更新，返回已持久化的序号。重试保持同一批次 ID，避免重复消息。旧代次的流式事件不能在历史改写或删除后把内容写回来；队列仅在确认成功后移除对应数据。

   Renderer 的变更入口显式标记被修改的消息、运行或提案。移除整个 messages 的深度监听，禁止以全量 JSON 比较来发现变化；消息有序 ID 列表和按 ID 存储的内容分离，避免为更新一个字段复制所有历史 ID。只更新当前消息或当前运行的版本。

   流式展示继续合并到动画帧，持久化另用短时间窗口合并新增块，初始目标为 200 ms，正常负载下最长等待 500 ms。用户消息在请求模型前完成小事务保存；回复完成、审批决定、切换会话、重发、停止和正常退出按现有边界等待必要写入确认。实际参数由打包应用中的性能测试校准，不为每个 token 单独同步落盘。

   保存状态区分内存已接收、等待保存、已确认保存和保存失败。现有工具栏预留稳定的状态位置，不插入会挤压布局的临时错误块；普通结果使用浮层。持续失败时提供明确的重试、导出未保存内容和存储管理入口，不再以一次短提示代替恢复流程。新变化和开始重试不能提前清除失败状态，只有对应数据得到确认后才能清除。

   导出未保存内容同时读取磁盘与待提交队列，以消息 ID 和代次去重，分块写入用户选择的位置；不能只导出最后一次成功保存的旧版本。磁盘不足时可以选择其他位置。正常退出等待所有确认，失败保持退出保护并呈现原因。强制退出或断电前尚未获持久化确认的流式尾部不能保证恢复，不能把其标记为已保存。

   写入积压按未确认字节数限制。达到高水位时以背压约束后续接收，不丢弃用户数据，也不让内存无限增长；重试有退避和错误分类。与会话有关的后台压缩、导出、索引工作必须可让出执行，不能长期阻塞新的保存。

   文稿写入继续复用既有 Core 事务、提案确认和版本校验。会话库与 Markdown 文件不是天然的跨存储原子事务；审批记录使用操作 ID 和提交进度关联，异常恢复先核对文稿版本和已完成记录，不能为了补写聊天状态而重复执行工具或覆盖新文稿。

6. **渲染改造**

   第一步先移除同步深度遍历和全历史正文指纹拼接；编辑监听只检查目标消息的 ID、版本、内容与附件变化。完成消息使用浅层、稳定引用，活动流式状态独立更新，审批等变化通过受控入口替换对应实体。不能直接将现有深层 ref 全部改为 shallowRef，否则嵌套更新会停止刷新。[Vue 性能说明](https://vuejs.org/guide/best-practices/performance.html)

   思考、工具详情、差异和子智能体详情在展开时加载、挂载；展开状态保存在组件外，以会话和实体 ID 标识。离屏卸载不丢展开状态、编辑草稿和未完成操作。计时器只更新活动运行的计时组件，不向所有历史消息广播当前时间。

   消息列表采用可变高度的虚拟列表，保留视口前后缓冲区。向上加载保留消息 ID 和像素偏移作为滚动锚点；字号、窗口宽度、Markdown 和详情展开造成高度变化时重新测量。继续保留手动上滚锁定，不能因新回复强制拉回底部。

   轮次导航从轻量索引获取所有轮次，跳转时先加载目标附近的消息；滚动定位使用缓存测量和索引查找，不再循环查询全部 DOM。导航标记本身也要限制实际挂载量，同时保持所有轮次可达和键盘操作能力。

   复制读取对应消息完整内容；选区覆盖的节点与正在编辑的节点暂时固定，防止虚拟列表回收破坏选择。审核跨消息拖选、全选、键盘焦点和辅助功能；若现有功能依赖原生全文 DOM，必须提供等价的模型级选择/查找行为并验收后，才能启用卸载，不能只验收可视区截图。

   详情按需加载不能改变业务判断。待审批、冲突、运行中请求及提案依赖从独立状态索引查询；操作前加载必要完整数据再校验。不能将“详情未加载”当成“没有待审批内容”，也不能把历史后缀改写限定在当前可见页。

7. **旧数据迁移与恢复**

   只在 Core 中读取旧 JSON；保留原始文件及迁移清单，不通过 Renderer 全量加载再回传。迁移读取与常规旧存储写入隔离，新写入在切换期间通过统一调度排队或持久化到独立的迁移待处理记录，不能有两个写者同时修改旧文件。

   迁移按 scope、会话和消息分批写入新库，记录原文件指纹、进度、格式版本和幂等键。针对大文件使用受字节预算约束的流式解析；不能沿用旧 readState 的累计容量限制而拒绝迁移，也不能一次把全部对象展开到内存。错误或未知字段保存在隔离的原始记录中并明确报告，不得通过解析器静默丢弃。

   切换前验证每个会话的消息数量、ID、顺序和时间，并对正文、原始工具参数、思考、提案与撤销数据做逐字段或内容哈希核对。全部验证完成后写入迁移完成标记，再让新库成为唯一历史写入源；未完成时可以重启继续，不把半成品标为成功。

   如果旧磁盘版本未超限，但当前内存已经有保存失败的新内容，必须将待写队列一并导入后才能切换完成。已经因重启消失、且从未落盘的内容无法由迁移凭空找回；升级前应先完成未保存内容的恢复或导出。

   旧版 localStorage、按阶段历史 key 和按作品历史 key 继续兼容，复用已有合并与并发保护语义。迁移涉及会话偏好设置时一并验证，不能遗漏所选模型和运行选项。

   旧 JSON 只代表迁移前的恢复点，不是新会话的自动回滚来源。迁移完成后禁止静默回退到旧 JSON 写入；新版本异常时使用仍认识新格式的修复版本。若要支持降级到旧版本，必须先验证完整导出能被旧版本读取且不超其限制，否则应明确阻止该降级路径。

8. **历史管理入口**

   保留点击历史条目切换的操作，增加菜单形式的导出、软删除和恢复入口，管理面板显示会话占用与运行记录占用。普通用户不需要理解数据库、WAL 或迁移细节。

   正在运行或仍有待处理提案的会话不能直接删除；引导先停止运行或处理提案，不自动中断任务。删除使用事务和代次标记，阻止旧保存请求恢复已删除会话。软删除提供恢复入口；彻底删除才释放无引用内容，并进行风险确认。单个会话的管理不影响其他作品或全局模型偏好。

9. **实施顺序与代码范围**

   第一步建立可重复的性能夹具、容量失败及重启读取用例，完成实际 Core Utility、工作线程和目标安装包的 SQLite 能力验证。冻结当前发送、恢复历史、改写、审批、撤销和退出的行为断言。

   第二步按职责拆分超限文件，落地消息变更入口、保存状态机、持久化契约和 Core 存储服务。重点是 `useAgentConversation.ts`、`conversationPersistenceState.ts`、`RendererStateStore` 及其调用链；将 controller 收敛为薄编排，不在约 3,000 行文件上继续堆叠实现。既有可复用模块应接入并去除重复职责。

   第三步完成增量写入、兼容适配与迁移，在真实磁盘上验证超 64 MiB、超 256 MiB、断点恢复和审批一致性。此时先保留现有界面，避免同时调试数据迁移与虚拟列表问题。

   第四步接入消息分页、独立业务索引、详情懒加载、虚拟列表和轮次导航，再补历史管理。`AgentConversation.vue` 的滚动、计时及编排职责拆入已有 composable 体系，视觉沿用全局主题、PopupSelect 和浮层反馈规则。

   第五步完成回归与打包验证后一起交付。新存储不进行长期双写；兼容层仅用于迁移和受控恢复，不能重新构造全历史大对象作为日常保存接口。Worker 入口、electron-vite 配置、安装包包含规则、关闭顺序和边界检查必须同步覆盖。

10. **验收门槛**

    功能：覆盖所有会话入口、恢复后的完整详情、普通与自动审批、代次依赖、拒绝与冲突、接受后撤销、停止与重试、子智能体、修改重发、选区插入、复制、轮次跳转、浅色/深色/自定义强调色，以及全部允许的 UI 字号。新旧实现在相同事件输入下，业务结果和恢复出的数据应等价。

    容量：单个作品历史超过 64 MiB、总历史超过 256 MiB后继续发送并重启，所有已确认数据完整恢复；一个超大会话不会阻止另一个会话保存。超大单条工具记录通过分块导入和读取验证，不能换成新的隐式累计上限。

    故障：在事务开始前、提交前后、确认返回前、迁移各阶段、审批文件写入与会话状态写入之间中断进程。验证无重复、无已确认数据丢失、无提案二次执行，未确认范围可识别；模拟磁盘不足、权限错误、损坏记录、工作线程重启及延迟确认。

    性能：复用前述 100 轮夹具，并扩展至 1,000 轮以及超过旧总容量的磁盘历史。相同机器上，日常流式状态应用 p95 目标低于 8 ms，输入到下一次绘制 p95 目标低于 50 ms；100 轮增长到 1,000 轮时，流式更新不访问旧消息详情，日常持久化不复制或遍历完整历史。验收需要分清状态处理、IPC、磁盘确认和实际帧时间。

    性能：空会话及短会话启动、首屏、输入和切换不能有可重复的明显回退；以同机预热、多次采样和 p95 比较，初始回退预算为 10%，同时记录绝对值排除计时噪声。长会话输入和滚动过程中不得周期性出现由本方案新增的超过 50 ms 的主线程任务。

    资源：固定可见窗口下，挂载节点、Renderer 详情缓存和已确认消息缓存应在预设预算内稳定；反复切换、展开和关闭详情后不持续增长。统计 Renderer、Core、存储工作线程和 Agent 各自内存、CPU、写入字节及待确认队列，不能只把卡顿转移到另一个进程。活动输入本身的大小和现有 Agent 模型上下文增长单独报告。

    平台：Windows x64、macOS arm64/x64 的实际 Utility 工作线程启动、SQLite 事务、重启恢复及退出均需通过；不以系统 Node 测试代替 Electron 安装包测试。实现提交前从仓库根目录运行 `pnpm verify`，并补相关持久化、迁移和安装包冒烟；仅格式化任务涉及文件。

方案完成时应同时消除全量渲染/保存热点与旧累计容量导致的拒写，并提供可见、可恢复的异常路径。任何以删除现有可见详情、改变模型上下文或弱化审批校验换取速度的实现，都不满足本方案的功能要求。


**实施记录（2026-09-11）**

以下是本次实际实现与验收结果；上文描述目标方案，未实施部分在末尾明确列出。

- Core 管理 SQLite 工作线程，使用事务、WAL/FULL、按消息路径的增量更新、分块暂存和稳定批次确认。已移除旧 JSON 每项 64 MiB、总计 256 MiB 的累计拒写规则；单次传输仍有字节预算。正文、原始参数、提案与撤销依据保留，重复文本按内容哈希复用并压缩，不按时间删除用户历史。
- 旧 JSON 通过 Core 流式迁移并保留原文件；原始未知字段和不符合会话结构的条目保留在原始记录中，不因一项格式异常阻止其余有效历史迁移。旧阶段 key 在 Core 内合并，避免 Renderer 重建整个作品的历史快照。旧客户端完整快照兼容入口保留并受并发校验约束。
- 会话控制器拆为按职责组织的模块，日常变更记录具体消息和字段；移除同步深度历史监听和全历史编辑指纹。加载期间暂停保存通知仍记录本地修改，解除暂停后补发；加载中的本地编辑不能被旧快照覆盖。
- 用户输入在请求模型前先保存，保存队列按短时间窗口合并变化；状态只有在收到持久化确认后才显示已保存。失败保留队列和原批次，正常关闭等待确认，失败保留界面与恢复入口。新变化或开始重试不会提前清除错误。
- 初始读取分页历史索引，只完整加载选中的会话；未打开的会话不读取全部详情。详情传输分块，读取时校验 revision/generation；页面与详情读取模块在找到实际会话后再加载，空历史不承担这部分解析开销。活动控制器仍保有完整功能数据，保证审批、撤销、修改重发和模型恢复历史使用完整记录。
- 折叠过程、工具、差异详情只在展开后挂载，活动计时局部更新，轮次导航用 DOM 索引；历史摘要只扫描足够的文本前缀。长消息列表采用分组 `content-visibility`，保留原生跨消息拖选、全选、查找和选区插入；未启用会破坏这些操作的 DOM 卸载实现，也未保留未接入的平行虚拟列表代码。
- 从列表移除作品或取消目录注册时，仅停止并释放运行态，保留该作品已确认的历史；重新打开同一个清单 ID 后仍可继续保存。实际删除项目才清理历史并保留旧请求隔离，防止“重新打开”和“旧请求写回”混为一谈。
- 历史菜单增加软删除和恢复，正在运行或待处理提案会话受保护。删除确认丢失期间的晚到编辑保留并隔离；重试确认原删除后转存到新会话，不恢复已删除的代次，也不清除其他会话的待确认队列。
- 历史菜单和保存失败状态提供当前对话导出。导出不依赖保存成功，捕获当前消息、草稿、已知提案/撤销/原始参数字段的稳定快照，分块写入 Main 授权的位置。临时文件同步后替换目标，确认丢失重试保持同一 token 和块序号；写入失败的半成品不能被误当成成功文件。

实际验证覆盖：超过 64 MiB 的历史与单条工具参数迁移、约 264 MiB 数据关闭重开后的逐页哈希一致性、超过 64 MiB 的分块导出、失败写入与丢失确认、旧文件迁移中断重试、Controller/队列/SQLite 的删除与加载竞态，以及真实 Electron Core/工作线程被强杀后的重启恢复。可重复入口为 `pnpm verify`、`pnpm smoke`、`pnpm smoke:conversation`、`pnpm smoke:shutdown` 和项目既有 `pnpm pack:test:mac:arm64`。

最终 `pnpm verify` 通过：578 个测试文件、3,249 项测试全部通过，格式、web/node/contracts/shared/runtime 类型检查、ESLint、边界检查和构建均成功。首屏就绪 JavaScript 为 998,042 字节，原 1,000,000 字节预算保持不变。真实 Core 崩溃/重开/分块导出冒烟通过；正常关闭冒烟确认最后写入保存且无工作线程重启或遗留进程。

`pnpm pack:test:mac:arm64` 按既有编排再次通过完整校验。实际 DMG 只读挂载后，包内客户端连续两次启动，分别确认首次写入和重启恢复；消息与草稿各 20 页回读一致，Renderer、Preload、Main、Core、SQLite 工作线程和 Faux Agent/三个 Utility 均启动成功。DMG 完整性及完整应用 ad-hoc 签名验证通过，开发 Electron 42.5.0 恢复后再次通过冒烟。

本次实现的边界：

- 完整正文 DOM 和活动会话业务数据仍会随会话增长；不能宣称已实现固定 DOM、正文内存或进程总内存上限。单条特别大的活动详情最终仍需为现有同步业务接口完整还原。已确认且访问过的会话也尚未全部改为可淘汰的业务缓存。
- 当前导出覆盖所选控制器和未保存内容，格式明确标注 `unknownDatabaseFieldsIncluded: false`；它不是整个数据库的原始备份，也没有增加一键导入入口。旧迁移文件是升级前恢复点，不是新版数据库的持续备份。
- 软删除提供恢复，不立即释放磁盘；尚未提供永久清理和完整容量统计面板。未确认字节高水位背压、跨存储审批事务协调和模型级全文选择/查找替代也不是本轮已实现的功能。
- 平台结论以实际运行记录为准；不能把既有旧版本 Windows 安装包、系统 Node 测试或仅存在 ASAR 文件视为新版 Windows/macOS x64 运行通过。
