## 1 结论摘要

长篇智能体的总体结构是对的：一个主创统管五个阶段，用“稳定业务 id + 五个通用 CRUD 工具”覆盖 14 类对象，规则放在不可编辑层，写入走提案，连续性走批次账本。这套骨架不需要推翻。

问题集中在三处：

1. **团队成员拿不到长篇规则和结构目录**（缺陷级）。短篇/剧本的子智能体会收到完整工作区规则和实时目录，长篇子智能体只收到两行说明，且上下文模式固定为全新上下文。成员不知道 id 前缀、document 名称、list 规则，也拿不到任何 volume_/chapter_ id，而 list 又不能查阶段顶层，只能靠主智能体在 task 里手抄 id。
2. **写一章要绕很多圈**。写一章需要的依据（章卡、叙事落点、事件、出场人物、伏笔触点、最近交接、前文结尾）分散在 10–20 次 list/read 里，每一次都重发整段上下文；批次账本下“上一章交接”还常常不存在。这是长篇最高频的工作，也是 token 和出错的主要来源。取材本身也没有边界：没有“写章读到哪里为止”的规则，`read` 只能全读、不识别重复读取，剪枝后又整批重读。方案建议把写正文需要的上下文前置到章卡：规划时写进章卡，写正文时基本只读章卡和上一章结尾（4.6）。
3. **上下文有缺口也有浪费**。追问轮丢失世界观/人物焦点；`activeRoot` 从未告诉模型；list 规则在五个地方重复；首轮世界观目录最多 2,000 条；世界观/人物焦点正文每次发送都读 2–3 份文档跨进程传过来，却从未进入提示词，读失败还会挡住发送。

建议分三期：一期只改 adapter 和 Renderer 的上下文组装（低风险，立刻见效）；二期补读能力（写作上下文写进章卡、读取护栏、全文检索、范围读取）；三期动协议（合并连续性提交、list 接口简化）。第 7 节列出需要你拍板的问题。

## 2 现状梳理

### 2.1 一次运行如何组装

```
Renderer useLongConversationCoordinator
  └─ LongWorkspaceRuntimeContext（导航快照、世界观目录、焦点、plotFocus、AGENTS.md）
Main → Agent: planWorkspaceRun (workspace-run-plan.ts)
  ├─ systemPrompt
  │   ├─ 基础准则 prompts-base.ts
  │   ├─ 【当前长篇智能体】+ 角色提示词 contracts/agent-prompts/long.ts（可编辑）
  │   ├─ 长篇工作区规则 prompts-long-rules.ts（不可编辑，约 3,500 字）
  │   ├─ 写入审批方式 write-approval.ts
  │   ├─ 正文图片保留规则
  │   ├─ （可选）联网搜索、资料库管理、团队管理附加说明
  │   └─ 本轮长篇工具边界（实际工具清单）
  ├─ tools: buildRunTools → buildLongWorkspaceTools
  │   list / read / create / edit / delete / query_linked_material_entries /
  │   load_skill / ask_user_question / propose_continuity_commit
  │   + 管理工具 + spawn_subagent + 联网工具
  └─ userMessage
      ├─ 首轮 buildLongFixedContextLines：书名、AGENTS.md、世界观条目目录、
      │   人物目录（每类 ≤50）、结构导航、list 规则、plotFocus、
      │   世界观/人物焦点定位、当前章卡
      └─ 追问轮 buildLongFollowUpContextLines：书名、AGENTS.md、世界观分类入口、
          人物类型入口、当前章卡、结构导航、list 规则、plotFocus
```

结构导航（`prompts-long-navigation.ts`）给出：全书计数、正文进度、连续记录位置、每卷前 50 个剧情点、以当前章为中心的章卡窗口（前 3 后 10；未选中时首 3 尾 10）。

### 2.2 工具面

| 工具 | 职责 | 备注 |
| --- | --- | --- |
| `list(stage, scope_id)` | 列出一个容器的二层结构 | 必须同时给 stage 与合法 scope_id；不能查顶层；叶子不能 list |
| `read(id, document?, chapter_id?)` | 一次读全文 + 精简 meta | 无预览/范围模式；登记“已完整读取”凭据供 edit 使用 |
| `create(kind, meta, content)` | 新建一个对象 | meta 是 30 个可选字段的扁平联合，必填项按 kind 在运行时校验 |
| `edit(id, document?, content/replacements/meta)` | 整篇写、片段替换、改 meta、卷内重排 | 覆盖非空文本前须已完整读取 |
| `delete(id)` | 删除并报告级联影响 | |
| `propose_continuity_commit` | 把连续若干已写章登记为一个账本批次 | 要求末章连续性文件已先用 create/edit 写好且非空 |
| `query_linked_material_entries` / `load_skill` | 素材、技能 | |
| `ask_user_question` | 简短询问 | 子智能体不提供 |

Core 侧已有 `long.search`（外部控制 `search_text` 在用），`LongQueryCommandEnvelope` 类型里也包含它，但长篇智能体没有对应工具，规则里明说“没有通用的全文搜索工具”。

### 2.3 上下文管理

- 剪枝：超过工作预算 50% 时，旧轮快照替换为占位，>800 字的旧 read 结果替换为“已读取…请重新读取”，旧写入参数里的正文替换为占位；并清空已读凭据。
- 摘要：超过 80% 时按 `TASK_FOCUS.long` 生成检查点，强调“只写引用，不复述”。
- 恢复：摘要后补回已加载技能，以及当前章正文结尾 1,500 字（经 Core 只读桥）。

### 2.4 团队成员

- `spawn_subagent` 子智能体复用同一套长篇工具（不含 `ask_user_question`），工具边界、写锁、抽卡都已就绪。
- 系统提示词 = 成员自己的提示词 + `longSubagentRequirements`（两行：单层子任务、只用继承工具、列出已提交修改 + 审批方式）+ 运行事实。
- `contextMode` 只在 adapter 类型里存在，contracts 和桌面端从未设置，所以长篇成员永远是全新上下文。
- 对照：短篇/剧本走 `writingSubagentContext`，成员拿到完整工作区规则和按已提交提案刷新后的实时目录。

## 3 问题清单

按影响排序。“证据”指当前代码位置。

### P0 缺陷级

**P0-1 长篇团队成员缺规则、缺目录。**
证据：`long-subagent-requirements.ts` 只返回两行说明；`run-tools.ts` 对长篇传 `longSubagentRequirements(input)`，没有 `buildLongWorkspaceRules`、导航和 AGENTS.md；`contextMode` 无人设置。
后果：成员不知道 `chapter_` / `arc_` 等前缀含义、人物与章卡需要 `document`、list 的合法容器；拿不到任何 volume_/chapter_ id，而 list 不能查顶层，只能靠主智能体在 task 里抄 id；抄漏一个就只能失败或乱猜。`docs/主要智能体系统提示词.md` 写的“团队成员复用同一份工作区规则”对长篇不成立。

**P0-2 追问轮丢失“用户正在看哪里”。**
证据：`buildLongFollowUpContextLines` 不含 `renderLongCurrentStageSection`；两类轮次都没渲染 `activeRoot`。
后果：用户第二轮切到另一个人物或世界观条目说“改一下这个”，模型拿到的仍是首轮焦点，或者根本没有焦点；正文阶段、连续性阶段也没有明确的“当前位置”。

### P1 效率与正确率

**P1-1 写章节的取证链过长。**
写一章的标准取证：`read 章卡/card` → `list plot chapter_`（落点、伏笔触点）→ 每个落点 `read placement_`（写作指引）→ 相关 `read event_` → 从事件 characterIds 找出场人物 → 每人 `read core_profile` + `read current_state` → 找最近交接 → `read 上一章 body`（只为结尾，却必须全读）。合计 10–20 次调用，每次重发整段上下文。剪枝后这些 read 又被清掉，续写时再读一遍。

**P1-2 “上一章交接”与批次账本不一致。**
角色提示词要求“写章节前读取上一章的交接”。但批次提交只在检查点章写 handoff，批内中间章和“已写未提交”章都没有交接。模型找不到时要么读空文档，要么把几章正文全部读进来。目前没有“最近检查点之后发生了什么”的概念。

**P1-3 list 规则五处重复，接口本身易错。**
同一套“stage 与 scope_id 匹配、叶子不能 list、continuity 不收 arc_”出现在：系统规则、每轮用户消息里的 `renderLongListScopeGuide`、list 工具说明、`scope_id` 参数说明、`stage` 参数说明。重复这么多遍本身就说明接口容易用错。而且 `renderLongListScopeGuide` 里还混入“切换章卡主剧情点用 edit…”这样的写入规则，每轮随用户消息重发。另外 `plot` 的卷视图已经带正文状态，`draft` 视图几乎是它的子集。

**P1-4 首轮世界观目录过大。**
证据：`LONG_WORLDBUILDING_DIRECTORY_MAX_ITEMS = 2_000`，首轮逐条列出。2,000 条约 6 万字符，可能占去数万 token，而人物目录每类只给 50 条。

**P1-5 能力已有但没开放：全文检索、范围读取。**
- 一致性检查（“某人第一次出现在哪章”“这件法器叫过什么名字”）在上百章的书里只能逐章全读。Core 的 `long.search` 已经存在并有外部控制在用。
- `read` 只能全读。续写只需要上一章结尾，检查只需要开头，也必须读完整章。恢复逻辑里的 `longTail` 已经证明“读结尾不发编辑凭据”可行。

**P1-6 世界观/人物焦点正文白读，且会挡住发送。**
证据：`useLongConversationCoordinator.ts` 发送前调用 `buildLongWorldbuildingFocusSnapshot` / `buildLongCharacterFocusSnapshot`，读取当前页（及概览）正文，单份最多 2 万字；adapter 渲染时只用标题和 kind，提示词明说“正文未注入”。读取失败会弹警告并中止发送。这是发送延迟和失败的无谓来源（与“世界观切换首次加载慢”同一条 Core 读取通道）。

**P1-7 连续性提交写入次数多、审批卡多。**
提交一个检查点需要：create/edit 章末状态、接续包、伏笔变化、世界观揭露，每个出场人物 current_state + history，最后 `propose_continuity_commit`。N 个人物就是 4 + 2N 次写入、4 + 2N 张文件卡，再加一张账本卡。用户审批模式下体验差，自动模式下调用轮数多。

**P1-8 写章取材没有边界，容易过量读取。**
证据：
- 角色提示词第 3 条要求写章前读“章卡、出场人物、上一章的交接和相关连续性”。“出场人物”没说读哪份文档，“相关连续性”没有范围，模型倾向于每个人物都读 `core_profile` + `relationships` + `current_state`，再把伏笔线、世界观条目逐个读一遍。
- `read` 只有全文模式（规则原文“没有预览模式”）。为了接上一章结尾，要读整章正文；为了确认一个设定，要读整条世界观。
- `read` 不识别重复读取：同一文档在本轮已经读过、内容没变，再读仍然整段返回。
- 剪枝把超过 800 字的读取结果换成“请重新读取”占位（`workspace-context-policy.ts`），模型续写时会把同一批材料再读一遍。
- 人物 `history` 是轨迹，写一章通常用不到，但规则里没有说“写章不读 history”。
后果：写一章进入上下文的材料常常是需要量的数倍，挤占工作预算，提前触发剪枝和摘要，摘要后又要重读，形成循环。材料多了也会稀释模型对本章任务的注意力。

### P2 结构与长期质量

**P2-1 缺“实际发生了什么”的章节梗概层（已决定不做）。** 章卡是计划，正文是全文，账本记录的是人物状态和交接。写到第 80 章想回顾第 12 章，只能读全文或看章卡（计划可能已偏离）。人物 history 是按人物切的，没有按章的剧情梗概。
**P2-2 create 的 meta 是 30 字段扁平联合。** 各 kind 的必填/禁填只在说明文字里零散描述，出错靠运行时报错再重试。
**P2-3 快照逐轮附在用户消息里，被剪枝时会改写历史前缀。** 影响提示缓存命中，与《Agent对话性能优化方案》是同一问题，本文不重复设计，只要求本方案的改动不加重它。
**P2-4 没有长篇默认团队模板。** 团队能力已具备，但长篇用户要从零写成员提示词；P0-1 修好后，几个高频分工（章节写手、连续性记录员、一致性审校）值得给出模板。

## 4 优化方案

### 一期：上下文组装（adapter / Renderer，兼容扩展运行时契约）

#### 4.1 团队成员获得完整长篇规则与实时目录（修 P0-1）

- 新增 `longSubagentContext(input, longToolSharedState)`，与 `writingSubagentContext` 对称，返回两个**惰性**函数（前一个成员落盘后再取，和短篇一样）：
  - `systemPromptRequirements`：`buildLongWorkspaceRules(locale)` + 写入审批方式 + 精简固定上下文（书名、AGENTS.md、世界观分类入口、人物类型入口、结构导航）+ 一句“这是主智能体委派的单层子任务，交回时列出已提交修改”。
  - `pureReadSystemPromptRequirements`：只读版规则（去掉创建/修改/删除/账本小节，保留对象定位与 list/read）+ 同一份精简目录。
- 导航要用叠加了本轮已形成提案的版本（`proposalOverlay.applyToIndex` 的结果），保证成员能看到主智能体刚新建的章卡。
- 实施补充：成员规则工厂支持异步解析，在成员启动时经现有只读桥刷新索引，再叠加提案；保留原有同步工厂，不新增跨进程命令。
- 不引入 `parent-snapshot`：全新上下文 + 目录已足够，继承主对话会让成员成本翻倍。
- 改 `docs/主要智能体系统提示词.md` 中关于成员复用规则的描述。

验证：单测断言长篇成员系统提示词包含对象定位规则与 volume_ id；只读成员不含写入规则；前一成员新建章卡后，后一成员的目录里有它。Faux 运行一次“委派成员写第 N 章”。

#### 4.2 每轮都告诉模型“用户当前位置”（修 P0-2）

- 新增一段统一的 `【用户当前位置】`，首轮和追问轮都渲染：阶段（`activeRoot` 映射为世界观/人物/剧情/正文/连续性）+ 具体对象（世界观分类/条目、人物/文档、plotFocus、当前章卡）+ 一行“需要时 read(...)”。
- 合并现有 `renderLongCurrentStageSection`、`当前剧情工作区`、`当前章卡` 三处，删掉重复行。

验证：追问轮切换人物页后，用户消息里的位置更新；五个阶段各一条快照测试。

#### 4.3 停止读取不用的焦点正文（修 P1-6）

- 焦点快照只保留定位所需字段（分类/条目标题与 id、人物名与文档 kind）。`buildLong*FocusSnapshot` 不再调 `readDocument`。
- contracts 中焦点 `text` 字段先改为可选并停止填充，保持向后兼容；确认无人读取后，再在三期删除。
- 实施补充：焦点增加可选的分类、条目、人物业务 id，避免同名对象或目录截断导致定位失败；旧快照仍可按标题定位。旧正文快照继续校验其长度和配套字段。

验证：发送世界观/人物阶段消息时不再产生 `long.readDocument` 请求；模拟读取失败时发送不再被挡住；adapter 渲染结果不变。

#### 4.4 规则去重、首轮目录收敛（修 P1-3 前半、P1-4）

- 从每轮用户消息里删除 `renderLongListScopeGuide`。list 规则只保留在系统规则（一处完整表述）和工具说明（一句话 + 合法容器表），参数说明只写格式。“切换主剧情点用 edit”移回系统规则的“修改”小节。
- 首轮世界观目录增加按分类截断（已定）：每类最多 200 条，总计仍为 2,000 条（沿用现有 `LONG_WORLDBUILDING_DIRECTORY_MAX_ITEMS`）。超出的条目不列出，提示用对应的 list 查询，与人物目录的处理一致。追问轮仍只给分类入口。
- 总上限没变，所以这项改动只防止单个大分类占满目录，首轮输入 token 基本不会下降。大书的首轮成本用 4.10 的基线测量观察，必要时再调。

#### 4.5 角色提示词对齐批次账本（修 P1-2 的提示词部分）

“读取上一章的交接”改为：读取最近检查点的接续包；检查点之后若有已写未提交的章节，读取它们的正文结尾（二期上线后改为“读本章章卡和上一章结尾”）。改内置提示词要把旧版指纹加入 `LEGACY_PROMPT_FINGERPRINTS`，中英两份同步。

### 二期：补读能力（新增只读工具，不改写入协议）

#### 4.6 写作上下文写在章卡里（修 P1-1、P1-2、P1-8）

章卡就是章纲，也是写正文的依据。写这一章要用到的上下文，在规划章卡时就写进章卡。这样写正文时基本只读章卡，不用再到处查资料。

##### 4.6.1 章卡里的“写作上下文”小节

- 规划或细化章卡时，在 `card` 里写一个 `## 写作上下文` 小节，内容按需包括：
  - 前情衔接：从哪里接上一章；
  - 出场人物在本章相关的状态与动机；
  - 本章会碰到的设定；
  - 要呼应的前情与伏笔；
  - 不能写破的点：还没揭露的秘密、还没发生的事。
- 只写本章用得上的，不抄整份人物档案或设定。
- **只是写作约定，不强制**：不改契约和章卡结构，不校验这个小节是否存在、写了多少，也不要求格式或来源标记。
- 写进角色提示词“剧情”一条：“细化到章卡时，把写这一章要用的上下文写进章卡的写作上下文小节，只写本章用得上的。”

##### 4.6.2 写正文时读什么

写进系统规则的“读取”小节和角色提示词第 3 条：
- 先 `read` 本章章卡，再用范围读取（4.8）取上一章正文的结尾，然后开始写。
- 章卡的写作上下文够用，就不再读其他对象；缺什么，只读缺的那一个对象。
- 章卡没有写作上下文小节时，照章卡写，同样只按需读取，不额外提问。
- 写正文时不读：
  - 人物的 `history`、`relationships`，以及整份 `core_profile`；
  - 没出场的人物，本章不涉及的设定；
  - 其他章的整章正文，需要时只读片段。
- 写作上下文和上一章实际结尾或最新人物状态有出入时，以实际情况为准，并在交回说明里指出。
- 写作中产生的新事实记进连续性账本，不抄进后面的章卡。

“读取依据”一条（角色提示词第 3 条）改为：“写章节前读本章章卡和上一章结尾；章卡写作上下文够用就直接写，缺什么只读那一个对象。改设定前读取受影响的人物与剧情。”中英两份同步，旧版加入 `LEGACY_PROMPT_FINGERPRINTS`。

##### 4.6.3 下一章还没有章卡时：直接问用户

- 正文挂在章卡下，没有章卡就写不了正文。用户让“写下一章”而下一章还没有章卡时，主智能体先用 `ask_user_question` 问一次，不要自行规划后直接开写。
- 选项：
  - 我先拟章卡，你确认后再写；
  - 先不写。
  - 客户端会自动附上自由输入项，用户可以直接写这一章的要点。
- 用户给了要点或确认章卡后，再按 4.6.1 建章卡、按 4.6.2 写正文。
- 团队成员没有 `ask_user_question`（`subagent-child.ts` 会过滤掉）。委派写章前，由主智能体确认章卡已存在；成员遇到没有章卡的情况，只在交回说明里报告，不自行新建。

##### 4.6.4 读取护栏（工具层兜底，不依赖模型自觉）

- **重复读取提示**：`read` 记录本轮读过的文档：内容指纹，以及读取结果是否还完整留在上下文。再次读取时，如果内容没变、上次的结果也没被剪枝，只返回一句“该文档自上次读取后未变化，原文仍在上文”，编辑凭据保留。
  - 需要剪枝器在把读取结果换成占位时通知 read 工具，把该文件标记为“已移出”。机制与现有 `onContextCompacted` 相同，但要细到单次调用。被移出或摘要之后，再读正常返回全文。
  - 这是正确性的关键：如果剪枝后仍返回“原文在上文”，模型就再也拿不到全文。必须有单测覆盖“剪枝后重读返回全文”。
- **大文档提示**：全文超过阈值（建议 8,000 字）时，结果末尾加一行“本文较长；只需结尾或片段时可用 range / search”。不截断，读全文的语义不变。

##### 4.6.5 委派

委派“写第 N 章”时，task 里只写章卡 id 和额外要求，不把章卡、设定或人物档案抄进 task。成员自己读章卡写正文。

验证：
- 单测：剪枝前重复读取返回短提示，剪枝后和摘要后重复读取返回全文。
- Faux：
  - 章卡有写作上下文时，写一章只有“读章卡 + 读上一章结尾 + 写正文”三类调用；
  - 下一章没有章卡时，先提问，不直接建卡写正文。
- 真实模型：对比 4.10 基线中“写一章”场景的读取字符数、读取次数、重复读取次数。

#### 4.7 开放全文检索（修 P1-5 前半）

- 新增 `search(query, stage?, cursor?)`，底层走现有 `long.search`。
- 结果把 `fileId` 映射回业务 id + document（用索引反查），不暴露文件路径和 file_id，符合“不要询问、推断或复述文件路径”的规则。每条给标题、业务 id、片段。
- 命中只是线索：规则写明“检索片段不等于已读，修改前仍须 read 全文”。
- 新增 `searchCompactor`：旧检索结果剪枝为“检索过 <query>，命中 N 条”。
- 同步修改规则里“没有通用的全文搜索工具”的表述。
- 只读成员也开放。

#### 4.8 范围读取（修 P1-5 后半）

- `read` 增加可选 `range: "head" | "tail"` 与 `max_chars`（默认 2,000，上限 8,000）。
- 范围读取不登记编辑凭据，结果首行注明“片段，修改前须完整读取”。
- 4.6.2 的“读上一章结尾”“其他章节只读片段”都依赖这项能力，所以与 4.6 同期上线，不再作为可选项。

### 三期：协议与数据（需要改 contracts，影响审批卡）

#### 4.9 合并连续性提交（修 P1-7）

- `propose_continuity_commit` 增加可选的 `documents`：`chapter_end_state`、`handoff`、`world_reveals`、`characters: [{character_id, current_state, history}]`，伏笔决策沿用现有字段。
- 提供 `documents` 时，工具一次性形成“连续性文件 + 账本登记”的合并提案，Renderer 显示为一张账本卡（可展开查看各文件差异）；不提供时保持现有两段式流程，兼容旧会话和团队成员提示词。
- 实施细化：合并型沿用 `long.ledger_commit_proposal` 事件，携带文件差异；`text_files_batch` 命令增加可选 `preparation`（文件批次、正文版本、稳定提交 id 与版本来源）。Core 在同一可恢复事务内校验正文与文件版本、写文件并登记，重试按提交 id 幂等；磁盘索引和账本记录格式不变。
- 契约顺序：contracts（工具 details 新增合并型）→ Renderer 审批卡 → 自动模式落盘顺序（先文件后登记，任一失败整批不登记）。
- 手机端暂不做（已定）：只改桌面端审批卡。

#### 4.10 基线测量（贯穿三期，一期开工前先做）

用现有子智能体调用追踪与用量记录，在一份固定夹具书上跑四个场景，记录调用次数、输入/输出 token、工具报错次数、首轮输入 token。“写一章”场景另记三项：读取进入上下文的总字符数（按文档类型分列）、读取次数、重复读取次数，以及本章是否触发了剪枝或摘要：

1. 新建一卷三章的章卡；
2. 写一章正文；
3. 写完后提交连续性；
4. 委派成员写一章。

每期结束复测，作为“是否见效”的验收依据。

#### 4.11 list 接口简化（修 P1-3 后半，可选）

- `stage` 改为可选，按 `scope_id` 前缀推断默认视图：`world_`→世界观，`chartype`/内置类型→人物，`volume_`/`arc_`/`chapter_`/`event_`/`foreshadow_`/`book_line`→剧情；只有看连续性时传 `view=continuity`。
- `draft` 视图并入剧情卷视图（剧情卷视图已经带正文状态），保留旧参数一个版本作为别名；旧角色仅有正文读取权限时继续返回原有正文目录，避免扩大读取范围。
- 效果：规则可以从一整段压到一张小表；模型最常见的 stage/scope 不匹配报错消失。

#### 4.13 create 的 meta 说明表格化（P2-2，小改）

- create 工具说明末尾附一张紧凑的 kind → 必填 / 可选字段表，替代现在散落的文字；运行时报错统一为“kind=X 缺少 meta.a、meta.b；可选字段：…”。
- 不拆成多个 create 工具。保持一个扁平 schema，是为了兼容只支持简单 JSON Schema 的 provider（现有设计意图）。

#### 4.14 长篇默认团队模板（P2-4，依赖 4.1、4.6）

在团队广场或内置模板中提供三位成员：章节写手（读章卡与上一章结尾 → 写 body）、连续性记录员（读批次正文 → 合并提交）、一致性审校（纯净只读 + search）。只作为模板，不默认启用。新建长篇团队内提供三位默认禁用、可编辑的成员；已有团队保持原配置。

## 5 不建议做的事

- **拆成按阶段的多个主智能体。** 现在的“一个主创跨阶段”是有意的设计，界面阶段只表示用户在看哪里。拆分会带来跨阶段协调和交接成本；真正的痛点是取证链长、成员没上下文，4.1 和 4.6 已经覆盖。
- **把更多正文塞进固定上下文。** 固定上下文只放目录和定位，正文按需读取，这个方向是对的。章卡是写这一章时才读的有界材料，不是常驻注入。
- **由程序自动拼装写章依据包（之前设想的“章节简报”）。** 程序分不清哪些内容对本章有用，拼多了就是新的上下文膨胀源。该写什么由模型在规划章卡时判断并写进章卡，用户可见可改。
- **章节梗概层。** 已决定不做；前情靠章卡写作上下文、上一章结尾和连续性账本。
- **章卡写成设定百科。** 写作上下文只写本章用得上的部分，超过上限就说明写多了。
- **按字数硬拦截读取。** 模型有时确实需要全文（改正文、做一致性检查）。工具层只做提示和去重，不拒绝合法的全文读取。
- **为子智能体默认开启 `parent-snapshot`。** 成本高；有规则和目录后，全新上下文已经能工作。

## 7 决定记录

已定：
1. **不做章节简报**：写作上下文写在章卡里，写正文时读章卡和上一章结尾即可（4.6）。
2. **合并连续性审批卡（4.9）要做**，手机端暂不做。
3. **不增加章节梗概层。**
4. **写作上下文放在章卡 `card` 里的小节**，不改章卡结构，不强制格式和篇幅。
5. **下一章没有章卡时直接问用户**（4.6.3）。章卡没有写作上下文时不提问，照章卡写。
6. **世界观目录上限（4.4）**：每类 200 条，总计 2,000 条。

所有决定保持有效；第 1–3 期已完成。后续长书实测沿用本次四场景指标，最初一期前真实模型数据不追溯回填。

## 实测后补充（2026-11-14）

- 不增加正文与章卡逐项强校验，正文效果仍由用户提示词控制。
- 新账本记录各章正文 SHA-256；正文变化标记待复核，恢复原文可回到版本一致。旧账本无依据时标为未核验。状态不锁定写作。
- `propose_continuity_commit` 增加 `review_commit_id`：先读完整批次正文及末章连续性文件，必要时先修订连续性文件，再提原记录复核；Core 原子校验全部依据版本并更新指纹，不新增账本。
- MCP 运行定位信息由现有 Renderer 持久化通道保存；重启后按原 runId 恢复目标与会话，未完成运行返回 interrupted，续接前核对落盘。
- MCP `toolUsage` 从主智能体与成员工具 trace 去重统计，不依赖模型自报数字；工具成功与作品验收分开。扩展真实模型场景补测另行进行。

## 工具参数兼容补充（2026-11-14）

- 连续性 list 支持 book_line 全书概览，返回分卷记账位置、待复核批次和具体下一步调用；仍按连续性读取权限校验。
- 读取章节时忽略与 id 完全相同的重复 chapter_id；不同章节 id 继续拒绝并给修正示例。
- 单独传 max_chars 默认 head 片段，不登记全文编辑凭据；明确传入 range 时保持原意。
- 归一化结果带固定前缀；MCP 按已知 read 工具的 trace 分开统计 directSucceeded / normalizedSucceeded，失败仍计入 failed，其他工具文本不能冒充归一化。
- 原错误调用重放与真实团队只读审校分别验收，不增加正文与章卡的强校验。
