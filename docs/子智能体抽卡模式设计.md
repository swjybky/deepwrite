# 子智能体抽卡模式设计

> 状态：第 1–8 节已实现，未提交（2026-10-02）。第 9 节“按需抽卡”2026-10-20 确认并实现，未提交。两期的自动测试与界面检查均已通过，真实模型的抽卡流程都还没有试跑。本文是实现依据；后续改动如需偏离，先改本文再改代码。

## 1 背景与目标

润色、起标题、写片段这类任务，同一个要求多跑几次，结果质量差别很大。抽卡模式让一个子智能体收到任务后在后台独立运行多次，得到多份候选，再由用户或评估助手选出一份，只把这一份交回主智能体。

一期目标：

- 团队成员多一个“抽卡模式”开关。只有运行模式为纯净·只读或纯净·无工具的成员可以打开。常规成员有写入工具，抽 N 次就会写 N 遍，所以不允许。
- 抽卡次数可配，2–10 次，默认 3 次。
- 选择方式分手动和自动。手动：全部候选跑完后，在 ask_user_question 的位置弹出选择卡。自动：由评估助手按可编辑的规则选择，它只有一个选择工具，并且必须以调用这个工具结束。
- 主智能体的调用方式不变，拿到的结果只有被选中的那一份。

一期不做：再抽一轮、手动模式下先让评估助手推荐、两份候选的差异高亮、按模型限流。

## 2 已确认的决定

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | 开关按成员配置 | 挂在成员编辑页“运行模式”下方。不同成员的次数和评估规则差别很大，所以不做团队级开关 |
| 2 | 同一任务的 N 份总是同时跑 | 团队没开并行也一样。整次 `spawn_subagent` 调用同时运行的子运行（普通任务、抽卡、评估助手）最多 10 个，多出的排队 |
| 3 | 手动“都不采用”按未完成交回 | 任务以失败状态交回主智能体，附上用户附言，由主智能体决定怎么改任务再派。依赖它的任务跳过。“再抽一轮”放二期 |
| 4 | 评估助手必须调用选择工具 | 任务消息开头和结尾都强调必须调用 `select_candidate`。没调用就结束时追问一次；仍未调用或评估出错，改为手动选择 |
| 5 | 评估助手的模型可单独配置 | 默认继承主智能体的模型，与子智能体“继承”的含义一致；也可以单独选模型、思考等级和温度 |

以下默认值实现时照此处理，可以再调整：

- 成员改回常规模式时自动关闭抽卡，但保留次数、选择方式和评估设置。运行时也只对纯净成员生效。
- 评估规则没改过就不存，直接用内置默认，这样以后改进默认提示词，老配置也能用上。“恢复默认”就是清空自定义规则。
- 每份候选都是全新的子运行。系统提示词、任务、前置交接和素材上下文完全相同，候选之间互相看不到，也不告诉它是第几份。
- 资料库管理成员恒为常规模式，不参与抽卡。扩展域的子任务（`workspaceAccess: "none"`）不读这个字段。

## 3 配置

### 3.1 数据结构

成员定义（`packages/contracts/src/agent-team.ts`）新增可选字段 `draw`。运行模式、模型模式和抽卡的 schema 放在 `subagent-settings.ts`，由 `agent-team.ts` 再导出：

```ts
draw?: {
  enabled: boolean;
  count: number;                 // 2–10，默认 3
  selection: "manual" | "auto";  // 默认 manual
  evaluator: {
    prompt?: string;             // 不填即用 DEFAULT_SUBAGENT_DRAW_EVALUATOR_PROMPT
    modelMode: "inherit" | "custom";
    modelId?: string;
    thinkingLevel?: ThinkingLevel;
    temperature?: number;
  };
}
```

- 自定义模型的校验规则与成员一致：选“单独配置”必须选模型和思考等级，思考关闭时必须选温度。两处共用一个校验函数。
- 缺省 `draw` 等于关闭。旧客户端读到会丢掉这个字段，退回普通运行，与纯净模式的兼容方式一致。
- `DEFAULT_SUBAGENT_DRAW_EVALUATOR_PROMPT` 放在 contracts，并从 `renderer.ts` 导出，设置页显示和运行时使用同一份默认文本。

### 3.2 Main 解析评估模型

`agent-team-run-mode.ts` 解析成员自定义模型时，同时解析已启用抽卡、选择方式为自动且单独配置了模型的评估助手，放进同一个 `subagentRuntimeConfigs`（按模型配置 id 索引）。`session/commands.ts` 中“自定义模型必须有运行配置”的校验同样覆盖评估模型。

### 3.3 设置页

成员编辑页“运行设置”在运行模式下方新增 `SubagentDrawField`：

- 抽卡开关（`AgentTeamSwitch`）。常规模式下不可打开，并显示“仅纯净模式可用”。
- 打开后显示：抽卡次数（`PopupSelect`，2–10 次）和选择方式（`AgentTeamSegmented`：手动 / 自动）。
- 选“自动”时再显示评估助手：模型（复用 `SubagentModelField`）和评估规则文本框（显示默认文本，提供“恢复默认”）。
- 开关下方的说明文字：每次委派后台生成多份结果，只把选中的一份交回主智能体，消耗约为 N 倍（自动模式另加一次评估）。
- 成员卡片的模式徽标后加“抽卡×N”。
- 草稿签名 `agentTeamDraftSignature` 必须包含 `draw`，否则改了抽卡设置也不会提示未保存。

## 4 运行流程

### 4.1 主智能体侧

`spawn_subagent` 的参数不变。成员列表中抽卡成员名后追加标记：“［抽卡×N：系统会自动生成 N 份结果并择优，只返回选中的一份］”，主智能体就不会再要求该成员“多给几个版本”。

### 4.2 抽卡

调度器照常按依赖和并行名额启动任务。任务属于抽卡成员时，由 `subagent-draw.ts` 接管：

1. 同时启动 N 个子运行，每个都通过 `runSubagentTask` 运行。进度事件带 `draw: { role: "candidate", index, count }`。
2. 整次调用共用一个子运行限流器（`concurrency-limiter.ts`，上限 10）。普通任务、每份候选、评估助手各占一个名额。抽卡任务本身只占调度器名额，不占限流器名额，所以不会互相等死。
3. 全部候选结束后统计成功份数：
   - 0 份：任务失败，摘要写明“抽卡 N 份全部失败”并附第一份的错误。
   - 1 份：直接采用，摘要注明其余几份失败。
   - 2 份及以上：进入选择。

### 4.3 手动选择

- 通过运行内核的 `requestUserInput` 发出 `source: "subagent_draw"` 的请求。请求带一个说明性问题（id `draw`）和 `draw` 字段：成员名、任务 key、任务原文和全部成功候选（id `c1`…`c10`、序号、子运行 id、全文）。
- 用户的回答复用 `AgentUserInputAnswer`：`selectedOptionIds` 为一个候选 id 或保留值 `reject`（都不采用），`text` 为可选附言。broker 在请求带 `draw` 时按候选 id 校验。
- 现在的 broker 每个运行只允许一个待回答的请求。改为由运行内核按先后顺序排队（复用容量为 1 的 `concurrency-limiter`）：前一个请求结束后才发出下一个，排队期间同样暂停空闲超时。这样并行时多组候选依次弹出，也顺带避免并行常规成员的跨阶段确认撞车。
- 选择期间其他子任务照常运行，依赖该任务的任务继续等待。等待选择不计入子智能体超时。

### 4.4 自动选择（评估助手）

`subagent-draw-evaluator.ts` 新建一个独立的子运行，进度事件带 `draw: { role: "evaluator", count }`，名称为“评估助手”：

- 系统提示词由两部分组成：评估规则（用户可改）和不可编辑的【抽卡评估运行边界】，后者规定只依据任务和候选判断、必须调用一次 `select_candidate`、不改写候选。
- 任务消息的开头先强调“读完后必须调用 select_candidate 提交选择，这是唯一有效的输出”，接着是原任务和编号候选，结尾再提醒一次。
- 唯一的工具是 `select_candidate({ candidate: 1–N, reason: string })`。工具结果设 `terminate: true`，运行在调用后结束。重复调用只记第一次。
- 运行结束而没有调用工具时，用 `followUp` 追问一次。仍未调用，或评估出错、超时，就发事件说明原因，改为 4.3 的手动选择。
- 候选总长度按评估模型的上下文预算截断：总字数取 100,000 和上下文窗口一半中的较小值，按份数平均分，被截断的候选注明“已截断”。
- 评估助手不读作品、不加载素材上下文，也不继承主对话。

### 4.5 交回主智能体

只有选中的那一份进入主智能体的上下文和 `depends_on` 下游的交接，前面附一行说明：

```
【抽卡结果】共 5 份（成功 5 份），评估助手选择第 3 份。理由：……

<候选 3 原文>
```

手动选择时写“用户选择第 k 份”，有附言就附上“用户附言：……”。都不采用时，任务以 `error` 交回：“用户没有采用这次抽卡的 N 份候选。用户附言：……”。

### 4.6 中止

停止主运行会中止所有候选、评估助手和待选请求，任务记为中止。

`subagent.draw_updated` 的 `phase`：

| phase | 含义 |
| --- | --- |
| `selecting` | 候选已跑完，等待用户选择（含排队） |
| `evaluating` | 评估助手运行中 |
| `selected` | 已选定，带 `selectedBy`（`user` / `evaluator` / `only-success`）、`selectedIndex`、`selectedSubagentRunId`、`reason` 或 `note` |
| `rejected` | 用户都不采用，带 `note` |
| `failed` | 全部候选失败，或任务被中止 |

评估失败转手动时先发一条带 `reason` 的 `selecting`，界面据此说明“评估助手未完成选择，已改为手动”。

事件路径与 `subagent.planned` 一致：adapter `subagent-events.ts` → `runtime-types.ts` → Utility `agent-event-envelope.ts` → Main `index.ts` 转发 → Renderer `event-kinds.ts` / `events.ts`。

## 9 按需抽卡（已实现，未提交）

### 9.1 背景与目标

固定抽卡每次委派都抽 N 份，N 份的要求完全相同，只靠随机性拉开差距。按需抽卡把“抽几份、每份往哪个方向写”交给调用方决定：用户在对话里提出（“#润色师 抽 4 张，分别偏冷峻、偏热烈、短句、长句”），或者主智能体按任务判断。主智能体调用 `spawn_subagent` 时，为这个任务逐条写出每份的差异要求，条数就是份数。不需要多个版本时不抽卡，只运行一次。

- 抽卡次数多一个“自动”选项，与 2–10 次并列。
- 每次最多 `SUBAGENT_DRAW_MAX_COUNT`（10）份，也就是固定抽卡可选次数的上限。
- 选择方式（手动 / 自动评估）与次数模式互不影响，照旧可选。
- 主智能体拿到的仍然只有选中的一份，前面注明它的差异要求。

本期不做：主智能体为评估助手指定额外的评估侧重；固定抽卡接受差异要求；整次调用的抽卡总份数预算。

### 9.2 已确认的决定

前两项由用户拍板（2026-10-20），后三项沿用现有做法：

| # | 决定 | 未采用的备选 | 理由 |
| --- | --- | --- | --- |
| 1 | 自动模式的上限固定为 10，不再选次数 | 次数下拉改为“最多 N 份”，按成员设上限 | 符合“上限就是普通抽卡的上限”；成员级上限多一个设置，但能控制成本 |
| 2 | 不填差异要求就只运行一次 | 自动成员每次至少抽 2 份 | “按需”包括不需要的时候；不抽时没有额外消耗，也不弹选择 |
| 3 | 只填 1 条：不抽卡，把这条要求并进任务运行一次 | 整次调用报错退回 | 报错会让同一次调用里的其他任务都不执行 |
| 4 | 超过 10 条：整次调用报错退回，提示删减 | 只取前 10 条 | 与任务数超限的处理一致；悄悄丢掉用户点名的方向不可接受 |
| 5 | 非按需抽卡成员收到差异要求：整次调用报错退回 | 忽略 | 与“普通团队成员不能指定资料库管理目标”一致；忽略会让主智能体以为已经按方向抽卡 |

### 9.3 配置

`SubagentDrawSettingsSchema` 新增 `countMode`：

```ts
draw?: {
  enabled: boolean;
  countMode?: "fixed" | "auto"; // 新增，缺省即 fixed，fixed 不存
  count: number;                 // fixed 时为份数；auto 时不使用，但保留
  selection: "manual" | "auto";
  evaluator: { ... };            // 不变
}
```

- 用新字段，不把 `count` 改成 `number | "auto"`。schema 是非严格对象，旧版客户端会丢掉不认识的 `countMode`，退回按 `count` 固定抽卡；改 `count` 的类型则会让旧版本整份团队定义校验失败。
- 切到自动时保留 `count`，切回固定时恢复原来的次数。
- 新增常量 `SUBAGENT_DRAW_VARIANT_MAX_LENGTH = 1_000`（单条差异要求的字数上限）。
- `savedSubagentDraw`：`countMode` 为 `fixed` 时不存，与“默认值不存”的规则一致；“开关关闭且全为默认值就整段不存”的判定加上 `countMode === "fixed"`。草稿签名经 `savedSubagentDraw` 计算，自动覆盖新字段。

设置页 `SubagentDrawField`：

- 抽卡次数下拉的第一项加“自动（按需，最多 10 份）”，后面仍是 2–10 次，不新增控件。
- 选中自动时，开关下方的说明改为：主智能体按你的要求或任务需要决定每次抽几份（最多 10 份），并为每份写明差异要求；不需要多个版本时只运行一次。消耗随份数增加。
- 次数和选择方式两处都有“自动”，靠标签“抽卡次数”“选择方式”和各自的说明区分；如果实际看着容易混，次数一项改叫“按需”。
- 成员卡片徽标：固定为“抽卡×N”，自动为“抽卡·自动”。

### 9.4 主智能体调用

团队里有按需抽卡成员时，`spawn_subagent` 的每个任务多一个可选参数；没有时 schema 里不出现，以免干扰模型：

```ts
draw_variants?: string[]   // 每条 1–1000 字
```

参数描述：“仅用于标有［按需抽卡］的成员。每条写一份候选相对 task 的差异要求，条数就是抽卡份数，2 到 10 条。各份共同的背景和要求写在 task 里，这里只写差异。不需要多个版本时不填，任务只运行一次。”

- 条数限制在执行时检查，schema 不设 `minItems` / `maxItems`，否则超量会在执行前整体校验失败，原因同 `tasks`。单条长度写进 schema，执行时再查一次（超长同样整次报错），保证事件载荷不超限。
- 成员列表的标记：`［按需抽卡：最多 10 份。要多个版本时在 draw_variants 逐条写出每份的差异，条数即份数；不填只运行一次。系统择优后只返回选中的一份］`。
- 工具描述追加规则（仅在有按需抽卡成员时出现）：
  - 用户指明了份数或差异方向，照用户的写；只说了份数，由你拟定互不相同、贴合任务的方向；用户没提但任务明显值得多试（标题、开头、关键段落的不同处理），可以自行决定份数，宁少勿多。
  - 用户要的份数超过 10，按 10 份执行，并在回复里告诉用户。
  - 差异是同一任务的不同处理方向（语气、节奏、视角、切入点、篇幅）。不同的任务拆成多个 task，不要塞进 draw_variants。
  - 不要在 task 里要求成员“给几个版本”。

`planSubagentTasks` 解析 `draw_variants`，逐条去掉首尾空白，丢弃空串，并把结果写进 `SubagentTaskRequest.draw`：

```ts
interface SubagentDrawPlan {
  count: number;            // 实际份数
  variants?: string[];      // 按需抽卡时与 count 等长
}
```

| 成员 | draw_variants | 结果 |
| --- | --- | --- |
| 固定抽卡 | 不填 | `draw = { count: settings.count }` |
| 按需抽卡 | 不填，或去空后为 0 条 | 不抽卡，普通运行 |
| 按需抽卡 | 1 条 | 不抽卡，任务末尾追加“【补充要求】……”后运行一次 |
| 按需抽卡 | 2–10 条 | `draw = { count: 条数, variants }` |
| 按需抽卡 | 超过 10 条 | 报错：“任务 k 的 draw_variants 有 12 条，超过上限 10，未执行任何任务。请删减到 10 条以内。” |
| 其他成员 | 填了 | 报错：固定抽卡成员说明“每次固定抽 N 份，去掉 draw_variants 即可”，其余说明“只有按需抽卡成员接受 draw_variants” |

条目可以重复，几条完全相同就等于固定抽卡（用户说“同样的要求抽 3 张”时可以这样写）。

运行入口改为看 `request.draw`，不再直接读成员设置：`subagent-runtime.ts` 里有 `request.draw` 就走 `runSubagentDrawTask`；`planned` 事件的 `drawCount` 取 `request.draw?.count`，按需抽卡时每个任务的份数可以不同。

### 9.5 候选运行

- 第 i 份候选的 `context.draw` 为 `{ role: "candidate", index, count, variant }`。
- `runSubagentTask` 给候选的任务消息追加一段：

  ```
  <原任务>

  【本份侧重】在满足上面全部要求的前提下，这一份按以下方向处理：<variant>
  ```

- 候选仍然不知道自己是第几份、一共几份，也看不到其他份的方向，以免“既然我是第 2 版就刻意写得不一样”。
- `started` 事件的 `task` 仍是共同任务原文，差异要求放在 `draw.variant` 里，界面据此分别显示。
- 前置交接、素材上下文、系统提示词各份相同，与固定抽卡一致。

### 9.6 评估助手

- 候选标题带上差异要求：`【候选 2｜侧重：偏热烈】`。任务消息开头说明“各份候选按不同侧重生成”。
- 【抽卡评估运行边界】在有差异要求时追加一条：“候选标注的‘侧重’是有意安排的差异方向。以原任务为准判断哪一份最合适：方向本身是否适合任务可以作为比较的一部分，但不要因为候选遵循了自己的侧重就判它偏离任务。”这条放在不可编辑的运行边界里，用户自定义的评估规则不用改。
- 截断预算照旧按实际份数平均分。评估助手事件的 `draw.count` 取实际份数。

### 9.7 交回主智能体

```
【抽卡结果】按需抽卡 4 份（成功 4 份），评估助手选择第 3 份（侧重：偏冷峻克制）。理由：……

<候选 3 原文>
```

- 只有一份成功时同样写明它的侧重。
- 用户都不采用时列出全部方向，方便主智能体换方向重派：“用户没有采用这次抽卡的 4 份候选（侧重依次为：1 偏冷峻；2 偏热烈；3 短句；4 长句），本任务未完成。用户附言：……”
- 1 条要求并进任务的情况按普通运行交回，不加抽卡说明。

### 9.12 测试与验证

- contracts：`countMode` 缺省为 `fixed`；旧配置照常解析；`variant` 长度上限；严格的候选对象接受 `variant`。
- adapter 计划：按需成员 0 / 1 / 2 / 10 / 11 条；空串丢弃；固定抽卡成员、普通成员、资料库管理成员填了都报错；团队里没有按需成员时 schema 不含 `draw_variants`。
- adapter 运行：每份候选的任务消息只含自己的侧重；`started.task` 是共同任务；评估消息的候选标题与运行边界含侧重；选中摘要写明侧重；都不采用时列出全部方向；`planned.drawCount` 按任务各自的份数。
- Renderer：下拉切到自动再切回固定，次数不变；`countMode: fixed` 不入库；切换次数模式会标记未保存；卡片徽标；抽卡卡片和选择卡显示侧重；对话记录读写往返。
- 运行验证：设置区与选择卡照 8 节的 harness 方式检查。Faux 模型触发不了子智能体，需要用真实模型确认两件事：用户说“抽 4 张……”时主智能体会填 `draw_variants`；用户没提时，主智能体不会每次都抽满 10 份。
