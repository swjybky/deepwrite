# 长篇普通章节和列表页的分栏拖动

在完整工作台上，长篇普通章节每改一次外栏宽度，就会重新渲染一次长篇编辑器和章节正文组件。短篇正文能跳过这两次渲染。长篇列表页还会在浏览器算完外层布局后更新内层列宽，触发第二轮编辑器更新和布局。

## 测量条件

- 基于 `accd0006` 在独立目录构建生产版。macOS 26.5.1，Apple M5，Electron 42.5.0，窗口 1400 × 800，设备像素比 2。使用临时用户数据目录，通过 Preload 和 Core 创建合成作品，从资源树打开真实页面。
- 对照为短篇正文、长篇普通章节、长篇章卡右列表。三处写入完全相同的分段中文文本，两本作品在同一工作台。先展开同一份 200 章目录，再切换页面。5,000 字基础样本中，三页左栏均有 218 个资源节点。章卡列表有 200 项，每页显示最多 50 项。
- 拖动聊天和写作区之间的外层分隔线。主进程通过 `sendInputEvent` 发送按下、来回移动和抬起，移动目标间隔 4 ms。目标宽度 350–690 px，往返周期 535 ms，每次持续 2.2 秒。记录浏览器实际收到的可信指针事件和外栏宽度变更。每组交替测试各页面，原速与 CPU 限速分开统计。
- 主线程耗时取 CDP `TaskDuration` 的差值除以实际宽度变更次数，再取各次运行的中位数。它衡量完成一次宽度更新平均占用的主线程时间。帧间隔另用 `requestAnimationFrame` 采样。组件计数在独立诊断轮次包裹实际 Vue 渲染函数，以免计数开销混入基准。采样期间同时统计 Main 收到的 `deepwrite:command`。

## 基准结果

| 每次宽度更新的主线程耗时 | 短篇正文 | 长篇普通章节 | 长篇章卡右列表 |
| --- | ---: | ---: | ---: |
| 5,000 字，空聊天，编辑 | 3.23 ms | 4.35 ms | 6.23 ms |
| 30,000 字，60 轮相同聊天，编辑 | 6.19 ms | 6.42 ms | 8.59 ms |
| 30,000 字，60 轮相同聊天，预览 | 6.62 ms | 6.43 ms | 10.83 ms |

以上每格为 3 次运行的中位数。5,000 字编辑场景下，每次宽度更新平均发生约 1.09、3.09、5.30 次样式重算，以及 1.00、1.00、1.74 次布局。本机原速的这些样本均无超过 25 ms 的动画帧间隔。普通章节在轻载编辑时多占约 35% 主线程时间，整轮耗时的排序也会随视图和内容变化。

在 4 倍 CPU 限速、30,000 字和 60 轮聊天下，编辑模式的帧间隔 P95 中位数分别为 17.6、17.6、35.2 ms。预览模式每页另跑两次，超过 25 ms 的帧间隔分别为 34/231、59/206、94/96。列表在两种视图里都最容易错过一帧，普通章节与短篇的慢帧差距在预览压力样本里更明显。[逐次计数、原始时长和独立时间线统计](2026-11-20-long-editor-drag/samples.json)

## 原因与对照实验

1. **普通章节会跟着分隔线渲染。** [布局 Store](../apps/desktop/src/renderer/src/stores/layoutStore.ts) 把实时宽度放进 `writingRightPaneViewModel`，每次改变都更新工作区模块。长篇模块直接把 `v-show` 用在 [LongWorkspaceEditor](../apps/desktop/src/renderer/src/components/LongWorkspaceModule.vue) 上。当前 Vue 的 `shouldUpdateComponent` 会为带运行时指令的组件进入更新，即使可见状态始终为真。133 次宽度变化对应长篇编辑器和 [LongManuscriptEditor](../apps/desktop/src/renderer/src/components/LongManuscriptEditor.vue) 各 133 次渲染。只在探针中移除已显示编辑器上的这条指令，两者都降到 0，宽度仍变化 132 次。[短篇](../apps/desktop/src/renderer/src/components/WritingWorkspaceModule.vue) 在可见条件稳定时，模块更新但正文编辑器渲染为 0。
2. **普通章节还有独立的响应式布局成本。** 单独隔离 `v-show` 后，整轮样式重算仍为 411 次。单独将长篇编辑器根节点的 `container-type` 临时切为 `normal`，编辑器仍渲染 132 次，样式重算降至 144 次，样式耗时由约 80 ms 降至 39 ms。该实验同时改变了容器查询的适用条件，可将开销定位到这条布局路径，尚不能归给某一条 CSS 规则。普通正文没有收到长篇内部列表的尺寸回调。
3. **列表会在外栏布局完成后重新分配内栏。** [列表尺寸监听](../apps/desktop/src/renderer/src/composables/useLongEditorPaneResize.ts) 根据容器宽度计算列表宽度和上限，并写回绑定了 grid 样式和把手属性的 [长篇编辑器](../apps/desktop/src/renderer/src/components/LongWorkspaceEditor.vue)。对照实验中同为 133 次外栏宽度变化，原实现有 244 次编辑器渲染、230 次布局。让 CSS 在探针中按相同的默认比例和下限确定列宽，跳过列表尺寸回写，分别降到 133 次、132 次；再隔离 `v-show`，分别为 0 次、132 次。在 350、380、460、520、690 px 五个宽度下核对了编辑区、正文、列表和聊天的边界及字号。压力实验中，两处都隔离后，2.2 秒内生效的宽度变化从 68–72 次增加到 95–96 次。
4. **列表本身也有重排和绘制成本。** 在 30,000 字、60 轮聊天的独立 1.5 秒 Chromium 时间线中，短篇、普通章节、列表分别发生 91、93、156 次布局，合计约 251、239、387 ms。列表页还记录到 10,320 个章卡行、主按钮和操作区的 Paint 事件。嵌套绘制事件的数量不能换算成掉帧数。各组有效拖动样本内的工作区 IPC 命令均为 0。

## 修复方向与验收

实时宽度只交给布局容器和分隔线，编辑器只接收折叠等确实会改变内容呈现的状态。保留长篇编辑器实例及其未保存内容。内部列表优先让 grid 在同一轮布局中解决比例、已存宽度和最小正文宽度；保留键盘调整、折叠布局及把手可访问值。窄栏容器查询应保留并单独测量，直接删除会改变现有布局。

验收时从完整工作台拖真实分隔线，同时检查普通章节编辑器更新数、列表每次宽度变化的布局次数，以及长文和聊天同时打开时的慢帧。11 月 16 日的组件夹具已验证当时的宽度继承修复；本次覆盖的是完整工作区的宽度传递。[前次报告](2026-11-16-long-pane-resize.md)

本次交付为性能诊断，隔离实验只在测试窗口中生效。结论覆盖所列合成样本、章卡列表与外层分隔线。用户实际作品、Windows 实机、高刷新率显示器、正在流式生成的会话以及其他类型列表的具体帧率仍待实测。
