# ccs-mode

## 流程

1. **读懂任务，先定规模。**
   - 先把 `references/features/README.md` 当索引找到相关功能页；跨多次对话的任务先按 [handoff](../handoff/SKILL.md) 读交接笔记。
   - **小改动**（单层、≤ 3 个业务文件、不改契约 / 存储 / 核心流程）：只读直接相关的代码文件，不铺开读全套 `design/` 文档和无关后端实现。
   - **标准 / 跨层改动**：按对应剧本沿完整调用链读功能页、代码与设计规范。
2. **判断类型，只读对应的一个剧本。** 不要一次读入全部剧本。

   | 任务类型 | 判断依据 | 剧本 |
   | --- | --- | --- |
   | 修 bug | 现有功能表现不对，有报错或复现步骤 | [playbooks/fix-bug.md](playbooks/fix-bug.md) |
   | 新功能 / 改功能 | 要新增或改变行为、界面、命令 | [playbooks/feature.md](playbooks/feature.md) |
   | 排查 | 问“为什么”“是不是”，或现象原因不明，先要结论不急着改 | [playbooks/investigate.md](playbooks/investigate.md) |
   | 原型 | 方案未定，要做几个版本比较后再选 | [playbooks/prototype.md](playbooks/prototype.md) |

   拿不准就选 investigate。剧本还只是占位时，按本文件的流程和常识完成任务，结束后按 [ccs-distill](../ccs-distill/SKILL.md) 与下文「B. 提炼剧本」补上。
3. **复述方案并对齐关键分叉。**
   - 用大白话说明：要做什么、不做什么、准备怎么做、怎样算完成，等用户确认再动手。
   - 只有改动对象、期望结果和做法都唯一明确时才可跳过确认，并在回复开头说明跳过了。但只要存在直观可见的交互或空态/异常分叉（如单行省略 vs 换行、悬停展示 vs 常驻、拉取失败隐藏 vs 回退兜底），**即使改动很小也先用一句话对齐再写代码**，避免返工。
4. **执行。** 按剧本走；剧本与 `AGENTS.md` 冲突时以 `AGENTS.md` 为准。
5. **完成前检查。**
   - 改完先运行 `pnpm exec prettier --write <本次改动文件>` 和针对性单元测试（从仓库根目录跑 `pnpm exec vitest run <仓库相对测试路径>`），确认通过再跑统一检查。
   - 按 [verify](../verify/SKILL.md) 跑统一检查：工作区混有其他任务未提交改动时运行 `pnpm -s ctl check changed --files <本次改动文件>`；干净工作区运行 `pnpm -s ctl check changed`；触及契约、根配置、依赖或检查脚本时运行 `pnpm -s ctl check all`。未再改代码不重复跑同一组测试。
6. **给出证据。** 回复里列出：跑过的检查命令、结果与耗时；用验证 CLI 实际操作的命令和关键输出；界面改动的代表性截图（存档到 `test/`）；未完成或未验证的项。

## 所有剧本共同遵守

- 光有测试不算验证，必须在隔离测试实例上实际跑起来看（`pnpm -s ctl env doctor`，未运行则 `env start`，命令见 `pnpm -s ctl help`）；独立操作尽量用 `&&` 串联成一条命令减少往返。
- 样式检查按改动大小分级：新增控件或布局重做先读 `DESIGN.md` 和 `design/` 对应规范，完成后跑 `ui audit` / `ui same`；局部微调直接复用现有变量与全局类，用 2–3 张关键对比/交互态截图验证即可。
- 改动保持小而独立，一次只做一件事；顺手发现的其他问题记下来告诉用户，不混进本次改动。

## 长期规则

### B. 提炼剧本

**触发：** 用 ccs-mode 完成了一个真实任务而对应剧本还只是占位，或合作中沉淀出值得固化的有效做法与用户纠正。

**做法：** 完整提炼流程（证据采集、6 级落点优先级、占位补全与新建判定）见 [ccs-distill](../ccs-distill/SKILL.md)；只有工作流足够独立、会反复发生且无法并入已有剧本时才新建剧本，并同步更新上方「判断类型」分派表。各已有/占位剧本必须包含的核心步骤：

| 剧本 | 核心步骤 |
| --- | --- |
| fix-bug.md | 用 CLI 复现，证明问题存在 → 查功能地图和代码找原因 → 说明根因 → 修复 → 重跑失败场景证明已修好 → 跑统一检查 → 属于可能重复的错误时，按 D 把它变成工具或规则 |
| feature.md | 复述需求 → 查功能地图确认影响范围 → 实现 → 用 CLI 实际操作并截图 → 回归检查受影响的功能 → 更新功能地图 → 跑统一检查 |
| investigate.md | 不急着修。输出：已知什么；查了哪些数据（日志、接口、数据库、git 历史）；几个假设及各自依据；建议先验证哪个 |
| prototype.md | 同时做两三个方案 → 用 CLI 分别操作、截图、测量 → 对比优缺点 → 交用户选择 → 选定后清理未选中的方案 |

写法：
- 只写步骤和每步的完成标准，不写空泛原则。
- 每步尽量指向具体工具：验证 CLI 的哪个命令、功能地图查哪一节。
- 这次任务里用户纠正过的地方，写成剧本里的明确步骤。
- 最后一步必须是给出证据。
- 控制在一页以内。
- 写完提醒用户审阅并提交 git。

### C. 检验剧本

**触发：** 每写完或大改一个剧本（含 [ccs-retro](../ccs-retro/SKILL.md) 与 [ccs-distill](../ccs-distill/SKILL.md) 改完剧本或分派表后）。

**做法：** 提醒用户开一个全新对话，用下面的提示词测试，再根据反馈修改剧本：

> 请只根据 ccs-mode 技能和相关剧本，完成这个任务：<真实小任务>。过程中如发现剧本说不清、走不通或遗漏的地方，任务完成后列出来。

### D. 日常维护

**触发：** 智能体没按剧本执行，或按剧本执行了仍然出错。

**做法：** 按 [ccs-retro](../ccs-retro/SKILL.md) 还原断点并按仓库分层定位根因（偶发且已有门禁有效时无需调整流程），能改的按下面顺序落点，越靠前越好：

1. 能变成工具的，加进验证 CLI（`tools/control/`）。
2. 能变成规则的，走第三层：加 lint 规则或检查项，并在 `rules/README.md` 记下来历。
3. 属于跨任务规范或功能入口缺口的，补进 `references/features/`、`DESIGN.md` / `design/` 或 `AGENTS.md`。
4. 以上都不行，才修改剧本文字。

目标是剧本越来越短，越来越多的内容由工具和规则接管。
